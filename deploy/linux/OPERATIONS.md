# 运维与受控恢复

适用本仓完整发行物和 `deploy/linux` 的专用 Compose 拓扑。首期交付停写冷备份与同版本、同 CPU 架构恢复；不实现在线一致性备份、PITR、跨架构数据库转换或生产高可用。备份时间、停止时间和实际恢复时间均须实测后记录，不能由开发容器耗时推算厂区 RPO/RTO。

## 私有诊断

在部署目录执行 `./svm.sh diagnostics`。它检查容器状态，分别读取 API/Worker 的私有诊断，并在本部署独立 vhost 查询 RabbitMQ 队列的 ready、unacknowledged 和 consumer 数量。离线镜像环境使用 `./svm.sh --offline diagnostics`，继续核对既有镜像锁。

- `/health/live`、`/health/ready` 和 `/health/operations` 只在私有技术端口监听，Compose 不发布该端口，Nginx 不转发；不是新的公共管理 API。Worker 的 ready 包含消息连接，API 的 ready 允许 Broker 暂时断线而继续登记 Outbox。
- 数据库诊断使用受限 reader，每条查询最多 3 秒；总诊断预算 6 秒，同一进程缓存 15 秒且最多一个采集执行。超时/不可读返回 `Unavailable/Incomplete`，不以零积压或零故障代替未知。
- 包工作、任务工作、GitLab 工作、Outbox、开放下载及异常副本各自最多统计 1001 条，输出上限 1000 和 `capped`；工作样本最多 20 条，只含标识、阶段、租约代次和错误码。任务工作没有创建时间，因此不虚构其积压年龄。
- `replica.stale` 使用本节点配置的两倍副本巡检间隔；诊断不做文件散列和网络修复，不代替业务供包时的实测。磁盘剩余值取包根所在文件系统。
- 下载采集只读最多 200 个日志分段和对应 offset，报告未收集字节数及采样最早分段最后写入时间。超过上限会标记 `capped`，不是全量统计，也不读取日志正文。文件缺失或不可读明确报告。
- RabbitMQ 查询限本项目 vhost，命令等待上限 10 秒；队列行数按该 vhost 实际队列输出。数据库计数上限不适用于此列表，发现异常队列增长应单独处理。

API/Worker 输出结构化 JSON，只保留受控分类、异常类型、状态码、耗时和操作/工作标识；不格式化任意消息、异常正文、URL、请求正文、Cookie、密码或凭据。业务审计仍由原事务规则负责。Compose 使用 local 日志驱动，每服务 10 MiB × 5 文件轮转；可信下载分段不在本批自动删除，因为它们参与下载结束核实和包清理。磁盘阈值、通知接收人和日志留存周期由现场确认，当前不声称已有完整告警平台。

## 冷备份

备份包含明文私有配置、凭据校验材料、共享密钥保护证书和可能的 CA 私钥。目录必须放在受控存储中；传输、加密、访问审批及离线副本由部署方的既有制度执行。不要提交到 Git、上传公共 CI 附件或作为普通安装包分发。

先安排停写窗口，记录源部署、发行物提交、CPU、镜像摘要、厂区标识以及现场仍在执行的任务。已获许可的现场程序不会因平台停止而停止，需要独立登记其后续结果。

```sh
./svm.sh diagnostics
./svm.sh backup /绝对路径/新的私有备份目录
./svm.sh verify-backup /绝对路径/新的私有备份目录
```

工具按网关/API → Worker → RabbitMQ/PostgreSQL 的顺序停止本项目容器，要求数据库和 Broker 正常退出，检查没有运行的同项目容器、没有 postmaster.pid，才复制。不会停止其他 Compose 项目或执行开发库迁移。备份完成后源服务保持停止，不自动重启。若不是灾难切换，是否恢复源服务由本次窗口负责人明确决定。

备份清单覆盖完整 PostgreSQL 数据目录（包含角色，不是只导出业务表）、RabbitMQ 数据与定义、两份包目录/暂存/锁文件、可信下载日志与游标及未确认提交标记、运行与初始化配置、证书、厂区及节点身份、网关配置、完整发行物和许可材料。仅复制固定部署目录，不搜索宿主其他项目。每个文件保存大小和 SHA-256，拒绝链接、缺失文件、额外文件、覆盖旧备份和源目标重叠；最多 25 万条文件/目录项。输出未完成时保留现场，不把部分目录当作成功备份。

这是 PostgreSQL 17.11、RabbitMQ 4.3.6 原数据目录恢复，须保留原镜像版本、RabbitMQ 节点名 `rabbitmq`、UID/GID 和 CPU 架构。镜像归档通过原有 `./svm.sh export/import` 另外保管；目录备份不重复打包 images.tar。恢复机器要先取得记录的基础镜像以及完整发行物，不能用另一个版本的数据库试开数据目录。校验和用于完整性核对，不是备份来源的数字签名，只接受受控来源的备份。

## 隔离恢复与开放

```sh
# 在可运行相同版本工具的部署目录执行；目标必须全新且为空。
./svm.sh restore /绝对路径/私有备份 /绝对路径/新的恢复目录
# 同一宿主切换时，在源部署目录显式 down，释放原容器/网络；保留挂载数据。
# 不要使源服务与恢复服务同时运行。
./svm.sh down
cd /绝对路径/新的恢复目录
./svm.sh build
./svm.sh review-up 9461
```

恢复获得新的 Compose 项目标识，保留原厂区、用户、实例、软件、包、审计、幂等、Outbox/Inbox、任务及关联标识。下载网关改用新的进程代次；旧分段、游标和停止证明保留，不让新下载沿用已停止代次。恢复不覆盖源目录，不启动容器，也不自动迁移、播种、登记身份或重做业务。

恢复目录中的 `recovery/locked.json` 独立于数据库。普通 `up/apply/seed` 等入口受阻；Worker 即使被直接启动也拒绝工作。`review-up` 仅启动隔离内网中的数据库和 API，以及复核专用 Nginx 透传入口；只有固定转发到 api-a:7443 的入口连接接入网络并发布回环端口，API/数据库没有外部路由。不启 Worker/Broker，不连 GitLab。TLS 原样传递到 API，保留原证书名称校验；只能在本机或经受控隧道核实，不能关闭 TLS 校验。preview 备份恢复也需准备同一固定 Nginx 镜像，pull/export/inventory 会包含它。

核实期保留登录、改密、管理只读查询、实例报告、原回执、暂停投放、人工关闭未知，以及凭据/许可吊销和人员停用。人员停用仍经过原 `identity.manage`、CSRF、revision、幂等和最后管理员校验，不能借核实期启用人员或加权。登记、恢复签发、上传、下载、新投放、领取和开始许可均受阻；平台不会把原来未知的结果改成成功。

开放前必须完成并留存独立证据：

1. 原部署已停止并保证不会重新接入同一厂区；若原部署在另一台主机，必须由现场负责人确认隔离。
2. 逐项核对备份后仍在现场执行的安装/回退、实际安装版本、回执，以及备份后发生的账号停用、权限收窄、凭据和许可吊销。先在隔离环境通过现有受权操作重新实施必要吊销/停用；恢复出的旧授权不能直接视为当前授权。
3. 未结束投放均暂停；准备中的投放必须有暂停原因。数据库中尚有效的旧开始许可仍会阻止开放，应核实其执行并等待许可截止，不能伪改时钟。暂停不停止已经运行的现场安装。
4. 核对 Outbox/Inbox、包上传/复制/清理和 GitLab 待处理工作、未确认提交标记及外部执行记录。已有包工作可以在显式开放后沿原工作继续，不创建新的业务操作来“补一次”。
5. 共享保护证书、数据库角色、实例凭据验证材料、来源绑定和固定节点身份完整。开放工具重新读取受限数据库事实，并核对备份包文件；所有 Ready 包的两个副本须与数据库大小及摘要匹配，否则保持隔离。缺失原材料应恢复可信副本或重新选择完整备份，不修改状态伪造就绪。

将 [核实模板](recovery-review.template.json) 复制到恢复目录内的私有文件，实际完成后才填写 true：

```sh
./svm.sh reopen /绝对路径/私有核实记录.json
# reopen 保存审批事实，停止隔离容器/网络；仍不启动正常服务。
# 再次确认源端不会复活后，由部署人员明确执行：
./svm.sh up
./svm.sh diagnostics
```

工具检查最近两分钟的只读数据库报告、待执行投放/许可约束及包摘要，保存带时间和报告摘要的 `recovery/approval-*.json`，最后才移除隔离标记。任何失败保留隔离和原材料。开放后原暂停投放保持暂停，需人员按既有权限明确继续；不会自动投放版本或根据恢复结果填写现场版本。

`recovery/operation.lock` 防止同目录同时进行两项运维操作。中断后不要盲删锁；先检查本次拥有的容器、部分输出和是否仍有复制进程，确认无人写入后再由负责人处理。备份和恢复不设短总超时，大数据量要预留停写窗口；取消或错误绝不自动开放。

## 发行与整体回归材料

完整 Release 附 `release.json`、`sbom.cdx.json`、`build-inventory.json`、`THIRD-PARTY.md` 和许可材料。SBOM 按 [CycloneDX 1.6](https://cyclonedx.org/docs/1.6/json/) 描述后端已发布依赖和保守的网页运行依赖闭包，构建/测试依赖、原生平台包、声明的浏览器版本独立列示；不把浏览器构建工具当成服务器组件。

针对实际目标架构镜像生成独立清单：

```sh
eng/node deploy/linux/inventory.mjs --deployment /部署目录 --output /新的私有交付材料目录
```

记录实际 image ID、平台、固定 RepoDigest、厂商版本、OS 包清单和镜像自带许可归档。SDK/Node/npm 的许可随 Release 保留，浏览器清单明确区分声明与实测。组件清单、许可材料和漏洞扫描结论各自独立；不能把 npm 扫描零告警写成全部镜像无漏洞或允许任意再分发。企业 PKI、真实 GitLab、原生公司 Linux 和厂家安装仍须在统一回归记录实际结果。

开发侧专用流程：`eng/node deploy/linux/verify-operations.mjs --deployment <新建 full demo> --results artifacts/test-results/operations-recovery/linux`。它通过真实 HTTPS 建立虚构身份、版本和待处理工作，冷备、隔离恢复、核实后明确开放，检查旧会话/凭据、包摘要和暂停任务。最终停止其源端和恢复端；私有目录的清理另行登记，不报告尚未删除的材料为零残留。固定 Architecture 加上实际受影响选集即可，不需要把这次运维改动扩成全面业务回归。
