# 制造业软件版本管控平台需求规格说明

> 状态：既有需求已审阅；本次已按复核后的计划实现硬件台账、工控机归属、自动编号及核心工作台；角色及现场范围、PLC 归档继续后续实施。本文是业务规则唯一正文，不代表新能力已经实现。生产 API/网页已落地核心工作台并追加兼容迁移，实际覆盖见框架设计第 11 节。GitLab 导入、实例上报、版本包及 Update 已有局部验证；PLC 归档、细化权限及网页 GitLab 绑定仍待实现，系统及现场验收未完成。

## 1. 目标与范围

平台面向制造现场的上位机、视觉等软件，包括公司自研和外部厂家开发的软件。每个隔离厂区在本地网络内独立部署、维护账号、工序、设备台账及设备与软件映射，不依赖或同步任何既有业务平台的身份、主数据或业务。服务端计划运行在 Linux，技术栈为 .NET 8；受管软件可使用 EXE 或安装包，目标操作系统由接入方说明。

平台以“厂区 → 工序 → 设备 → 工控机／PLC → 对应程序”为现场入口。人员先定位设备、选择已关联软件，再按来源导入正式版本或人工上传/测试发布，完成目标投放和结果追踪；设备详情展示名称、编号、软件分类、安装版本、更新详情、历史、接入启用状态、运行状态、IP 和上报时间。软件产品的版本目录由多台关联设备共用，各实例分别保存安装和运行事实。

**交付边界：本项目只开发 Linux 上的 .NET 8 服务端、网页管理端、自有管理/接入 API 和接入文档。**上位机、视觉等可执行软件由接入方开发并按同一契约接入，接入方负责本机安装、运行状态报告、更新、回退及数据保护；本平台不规定内部更新进程或安装器。自有 API 供获授权调用方使用，不表示与既有业务平台建立集成、数据同步或共享身份。

一台设备可配置多台工控机和多个 PLC。工控机用于明确上位机、视觉软件的安装位置，人员仍直接从设备查看全部软件。PLC 采用可复用的程序压缩包版本库，通过映射关联各设备的具体 PLC：API 或网页上传测试版，人员完成现场验证后转正式，无独立审批。归档与人工确认使用版本分别记录；本轮不定义自动备份采集、在线下装、安装回退或周期上报能力。

本文仅定义需求，配套文档按第 9 节分工承接；实际实现与验证状态见软件框架设计第 11 节。

## 2. 术语与事实边界

| 术语 | 本文含义 |
|---|---|
| 厂区 / 工序 / 设备 | 本部署的厂区信息、由平台维护的工序及其设备台账；设备具有稳定平台标识、设备编号和名称，期别称呼只是名称内容。 |
| 软件 | 一款上位机、视觉软件或 PLC 程序库；同一产品共享版本目录，可用于多台设备。PLC 归档能力为待实现目标，不沿用可执行软件的安装/上报协议。 |
| 设备与软件映射 | 由平台建立的多对多关联：一设备多软件、同类软件多处安装、一软件多设备；接入登记及任务选择必须符合该关联；客户端不能自行创建设备或修改归属。 |
| 工控机 / PLC | 设备内可有多个具名硬件对象，各有稳定标识及可选 IP。上位机、视觉安装关联工控机，PLC 程序库通过映射关联具体控制器，允许多个控制器复用；IP 不承担身份或自动映射职责。 |
| PLC 程序归档 / 确认使用记录 | 前者保存压缩包、版本、测试及人工发布事实；后者保存人员核实的现场使用版本、材料、人员及时间。发布和下载均不自动写入确认使用记录。 |
| 版本 | 某软件的一次有版本号、安装包和变更说明的发布记录。 |
| 测试版本 | 未绑定 GitLab 的人工上传来源，在包就绪后供测试、尚未转正式的版本。GitLab 来源不进入本地 Test。 |
| 正式版本 | 绑定 GitLab 的受保护正式 Tag 经来源/流水线/清单核验和双副本就绪后直接导入，或未绑定软件的人工 Test 经本地历史安装证据及结论发布。 |
| 可用版本 | 安装包仍可下载的版本；可用测试版供测试下载，可用正式版可作为更新或回退目标。停用后仍保留版本与操作历史。 |
| 受管实例 | 映射到平台设备的某个软件安装实例；同一设备可有多个实例，各有稳定安装标识和独立凭据，不能靠 IP 识别。 |
| 推送 | 人员从网页或获授权调用方通过管理 API 创建指定实例的版本任务；接入方调用接入 API 获取任务并回传结果。 |
| 接入启用 / 运行状态 | 接入启用由平台管理，运行状态来自有效上报；启用、发布、下载或获得许可都不等于现场软件正在运行。 |
| 发布历史 / 安装履历 | 前者是软件产品的测试、正式及停用版本记录；后者是某设备实例被有效上报的实际版本变化，二者分别查询。 |
| 最近上报 / 未上报时长 | 平台最后一次有效接受该实例状态上报的服务端时间及其距当前的时长；重复或旧报告的判定见详细设计第 5.1、8.1 节。超过阈值时页面显示“状态未知”，不能据此证明整台电脑断网或软件已停止。 |
| 安装与运行上报 | 安装版本、安装时间和运行状态均来自接入方的 API 上报，页面展示其上报值与时间。上传安装包、生成任务或下载完成都不能冒充已安装或正在运行。 |

## 3. 用户与权限需求

- **REQ-AUTH-01｜已确认**：网页和对外管理 API 都要校验软件范围及操作权限。只有具备相应权限的人员或系统可以登记软件、查看和下载版本、上传版本及发起推送；人工转正式按 REQ-REL-05 由有权人员完成；GitLab 导入使用绑定范围可信集成身份，不开放通用管理系统凭据。
- **REQ-AUTH-02｜已确认**：对上传、测试包下载、转正式、推送、取消、重试、回退和停用保留操作者或调用主体、时间、对象及对应操作所需的原因与结果，历史记录不得因版本切换或包清理而丢失。
- **REQ-AUTH-03｜已确认**：上传、转正式和推送分别按权限控制；同一名人员获得相应权限后可以完成这些操作，不强制由不同人员承担。转正式时由平台记录登录人员工号和操作时间。
- **REQ-AUTH-04｜已确认**：各隔离厂区独立维护平台账号和员工工号，不复用其他业务平台身份。每个管理 API 调用主体和受管实例使用各自有范围、可吊销的凭据。管理员为已有设备的固定工控机软件位置开通受限许可，固定软件、位置及修订、有效期与一个名额，实例引用平台已有设备完成登记；授权不作为日常共享凭据。
- **REQ-AUTH-05｜已确认，人员角色与现场范围已实现，现场验收待执行**：人员采用角色模板、独立操作权限与工序/设备范围组合授权。平台管理员、程序工程师、现场运维、只读人员是可解释的配置模板，不按名称硬编码放行；创建、维护、PLC 上传/发布、接入管理、投放/控制和共享软件来源/发布/停用分别授权。页面显示有效操作及范围；服务端对列表、数量、详情、下载、目标封存和写入统一过滤，撤权使旧游标和未提交草稿失效。现场范围不自动授予影响其他设备的共享软件管理权限；创建对象不扩张创建人的授权范围。已有授权保持原事实，迁移不得自动授予新范围或新动作。角色修改对全部已分配人员统一生效；每个角色的操作只作用于它自己的范围。工序范围覆盖其后新增设备，设备范围不扩展到同工序其他设备，硬件继承设备范围。创建台账 asset.create、关联 binding.manage 独立于修改和接入；人员权限变化不自动吊销独立实例凭据或已签发许可。

### 3.1 制造现场台账与软件分类

- **REQ-ASSET-01｜已确认**：本平台维护本部署厂区、工序和设备台账，设备必须有编号、名称和工序归属；现场导航为“厂区 → 工序 → 设备”。厂区稳定标识、名称、时区由显式配置提供，缺少配置明确失败；工序代码和设备编号厂内唯一且不可修改。名称中的一期、二期等称呼不拆成额外层级。聊天中的厂区、工序、型号和设备号只作举例，不得据此创建真实台账、种子或默认配置。
- **REQ-ASSET-02｜已确认**：受管可执行软件区分上位机与视觉分类，软件代码唯一，代码和分类不可修改。新工作区按 REQ-AUTH-05 核验有效权限，创建不自动增加来源、发布、停用、接入或跨现场管理权限；人员角色批次已取消新建软件自动授予 software.read、instance.read、instance.manage；历史直接授权原样保留，现场角色通过具体关联可见，未关联产品由管理员明确分配。每个软件产品独立管理版本和包，同一软件可关联多台设备，同一设备可关联多个软件；软件分类和设备映射不能复制出每设备一套软件版本编号。PLC 程序库同样可跨设备复用，按 REQ-REL-10 分别保存各控制器的确认使用事实。
- **REQ-ASSET-03｜已确认**：设备与软件映射由本平台管理，逻辑撤销保留记录，同一组合重新建立保持标识且修订号递增；旧操作键的重放不能再次改变映射。首次登记必须引用已有设备，并满足设备映射、固定工控机安装位置和本次许可范围；新位置只能登记一个实例，旧宽范围许可仅允许原成功结果核实；无设备、无映射、错误软件或无授权时不得创建身份、实例或消耗名额。设备编号、名称、工序不能由登记正文或 IP 自动生成、覆盖；已确认实例引用后映射不可撤销或改绑，已登记实例不能靠重试改绑设备。
- **REQ-ASSET-04｜已确认**：设备详情显示设备编号和名称、工序、关联软件及分类、实例安装版本、可用更新及说明、软件发布历史、实例安装履历、接入启用状态、最近运行状态、IP 和上报时间。无实例或无上报时如实显示；同设备不同软件、同 IP 不同实例保持独立。台账维护与软件查看分别授权，汇总及筛选不泄露无权软件详情或统计。
- **REQ-ASSET-05｜已确认方向，待实现**：PLC 采用设备内具体控制器的程序归档流程，按 REQ-REL-10 上传、验证和发布；不能套用上位机/视觉的实例安装、在线更新、回退或每分钟上报。IP、文件名及压缩扩展名不决定归属或程序类型。平台不要求能访问 PLC 网络。页面优先展示人工确认使用记录，不展示推断的在线/离线状态，不生成在线率或已下装结论；自动备份取得方式仍待后续设计。
- **REQ-ASSET-06｜已确认，工控机与台账部分已实现**：平台自动生成新工序、设备和软件的稳定内部编号，普通表单不要求人员编写代码；旧编号保持不变，可另外填写现场资产编号。人员在所选工序下创建设备，在设备内添加/复用上位机或视觉产品并选择所属工控机，或为具体 PLC 新建/复用程序库，归属由上下文带入并由服务端核验。同设备的多台工控机、同类软件安装和多个 PLC 分别标识；已登记实例不因补充归属而重建身份、历史或任务。新关联必须引用当前设备已有的具体硬件：上位机/视觉只能关联工控机，PLC 程序只能关联 PLC 控制器；服务端拒绝缺失、跨设备或类型不匹配引用。一个工控机可同时关联多个上位机和视觉，同一产品可在多个工控机各有独立安装。硬件归属在导航、关联及更新确认中明确显示。历史安装无法确定工控机时显示“待补充归属”，不得作为新更新目标，不能按名称或 IP 自动合并。

## 4. 软件与版本管理需求

GitLab 负责上位机、视觉的需求、开发、测试、合并及正式发布；本平台承接厂内分发和现场安装管理。新建产品以 GitLab 为主要来源，未关联时展示明确的待配置状态；已有人工产品及历史继续可追溯。PLC 使用独立的人工归档验证路径。研发分支、Issue 关闭或导入成功均不构成本平台自动安装规则。

- **REQ-REL-01｜已确认**：统一“软件工作台”支持按工序看设备软件概况、按设备内工控机/PLC 分组看程序、按软件看全部授权关联设备及具体硬件。主导航不再分别设置现场软件、软件与版本和更新任务；版本/来源、接入/IP 资料和更新记录按当前对象展开，硬件归属常显。GitLab 软件以正式版本为主，PLC 程序区分测试与正式归档，原人工软件保留历史；当前安装/人工确认版本和共享发布版本分别展示。软件选择器可搜索、分类和分页，支持几十至上百款产品，数量及结果统一权限过滤。更新直接从关联机台表逐个勾选安装位置，确认后进度留在原行，切换视图不丢任务；同机台两处安装不自动全选。范围切换、展示字段和查询选择行为见详细设计第 9.3 节。
- **REQ-REL-02｜已确认方向，绑定维护待实现**：GitLab 绑定软件由后台 HTTPS 拉取正式 Release。服务器连接、信任及只读凭据由部署人员私有配置；有权人员在网页选择该连接允许的项目及产物，与软件建立绑定，网页不接收或回显 Token。来源面板区分待关联、等待发布、同步、包处理、可用及失败，支持立即扫描和历史 Tag。绑定软件禁止人工创建及再次发布，旧人工产品保留网页/API 的既有能力。当前绑定仍由文件维护；网页修改绑定的授权、revision、审计及历史保护按详细设计第 9.3 节另行实现。
- **REQ-REL-03｜已确认**：GitLab 来源核对受保护 Tag、Release、清单、成功流水线及产物 Job 的项目/提交/Tag 关联；清单与安装包由同次构建交付，形成厂内双副本后直接成为 Formal，不重复执行研发测试或审批。人工来源每次上传必须关联软件、变更级别、更新内容、更新原因及安装包；平台记录上传者和时间、生成版本号。上传成功后只进入测试版本，不自动成为正式版本。
- **REQ-REL-04｜已确认**：未绑定 GitLab 的人工来源，测试人员可从网页下载测试包并自行在一台设备安装；平台记录下载人员工号和时间。转正式前，平台须收到至少一个测试受管实例通过上报 API 报告该测试版本。无需另填独立测试记录，也不要求单独的“正在运行”证明。
- **REQ-REL-05｜已确认**：具有该软件发布权限的人员在网页填写测试通过原因与结论并点击转正式；平台自动记录其工号和时间。此规则仅适用于未绑定 GitLab 的人工版本；GitLab 正式来源不要求本地证据、结论或再次发布。仅有测试版本上报不会自动发布，缺少该版本上报时不得转正式；采用同软件、版本 ID 和版本号一致的历史 Installed 证据，不要求 Running、当前快照仍为该版本或五分钟新鲜度。转正式时须两个固定节点副本健康且核对时间有效；发布资料及证据引用形成后不可修改，停用保留。
- **REQ-REL-06｜已确认**：GitLab 来源保存原 Tag、规范数字版本、提交、流水线/Job、源发布时间和包摘要；同 Tag 改写或不同来源占同一数字版本报告冲突，源删除不删除本地历史。人工历史版本的更新内容、更新原因、测试包下载记录、测试版本上报、发布原因与结论、发布操作和安装包对应关系应可追溯。
- **REQ-REL-07｜已确认**：GitLab 来源以 `X.Y.Z` 或 `vX.Y.Z` 正式 Tag 为版本权威，保留原 Tag，规范化三段数字（首段至少 1），不接收预发布后缀；首轮只导入最高合格版，其余历史指定 Tag，后续新发布不以版本高低作为导入条件。既有人工软件及 PLC 归档由本厂平台按各自版本库独立生成三段数字版本号。首版为 `1.0.0`；小改动增加修订号，稍大改动增加次版本号并将修订号归零，大版本增加主版本号并将后两段归零。网页和管理 API 不得绕过生成规则；请求提供的版本号不符合平台生成结果时拒绝。测试版转正式沿用原版本号；默认更新目标是编号最新的可用正式版，历史可用正式版可被明确指定为更新或回退目标。安装包内 EXE 的自带版本信息不作为平台编号依据。
- **REQ-REL-08｜已确认**：每次上传的安装包记录和内容不可覆盖；平台提供完整性校验信息，不能通过覆盖同一路径悄悄改变已发布包。
- **REQ-REL-09｜已确认**：可用版本的安装包保留供下载；可用正式版还可用于更新和回退。版本停用且不再被未完成任务引用后可清理包文件，但版本号、变更说明、下载和操作历史继续保留；已清理包的版本不可再下载或作为任务目标。
- **REQ-REL-10｜已确认方向，细化待复核**：PLC 程序库按产品独立编号和归档，可关联多台设备的具体控制器，一台设备也可使用多个不同程序库；非标程序可只关联一台。版本及发布事实共用，每台控制器的确认使用事实独立。网页或受限 API 上传压缩包、变更说明及资料，摘要和副本就绪后进入 Test；有权人员核对程序库、版本、验证所用的具体 PLC 及现场验证记录，填写结论后一次转 Formal，记录真实人员及时间，无独立审批。上传凭据固定允许的程序库、动作及验证对象范围，只允许归档工作，不具备发布、人员管理或现场下装权限。发布资料和包不可覆盖；使用流程为选择具体 PLC 与版本、下载归档、人员使用工程软件现场更新、另行登记使用事实；不要求平台连接 PLC。人工确认使用须当前现场范围权限，固定控制器、程序与版本，并保留人员、现场时间、登记时间、说明和原版本；下载无需强制由同一人员完成，但下载本身不是更新证明。测试期间可记录测试版的现场使用，该记录不自动转 Formal；不从上传/下载/Formal 状态推断现场事实。精确接口及迁移属于后续实现，当前没有可调用的 PLC 端点。

## 5. 接入 API 与状态展示需求

- **REQ-CLI-01｜已确认**：平台提供安装信息上报 API，接收受管软件与实例身份、接入方上报的实际安装版本、安装时间和地址，并记录服务端接收时间；接入方更新后再次上报实际安装版本。
- **REQ-CLI-02｜已确认**：平台提供版本和运行状态上报 API。页面展示实例最后一次上报的版本、运行状态及上报时间；超过未上报阈值时显示“状态未知”，不得据此推断软件已停止，也不得仅用版本号或下载记录推断正在运行。测试转正式只检查测试版本上报，不以单独的运行状态证明为前提。
- **REQ-CLI-03｜已确认**：网页可按工序、设备及对应软件查看受管实例、上报版本和运行状态、最近上报时间、未上报时长、IP、可用更新及最近任务结果；设备汇总受 REQ-ASSET-04 的权限过滤约束。
- **REQ-CLI-04｜已确认**：平台提供版本查询、目标任务领取、安装包信息与下载、执行结果回执 API。接入方调用这些 API 获取可用版本与分配任务；人员无需逐台打开网页检查版本。平台不规定接入方软件内部如何定时调用或执行安装。
- **REQ-CLI-05｜已确认**：厂家与自研的上位机、视觉软件遵循相同的 API 接入规则；PLC 程序上传按 REQ-ASSET-05、REQ-REL-10 使用独立受限身份与归档契约，不调用实例登记及更新协议。
- **REQ-CLI-06｜已确认**：网页显示实例上报的 IP，以及从平台设备台账取得的厂区、工序、设备编号和名称，可按上述信息筛选。设备映射与归属必填；未上报 IP 时仍可按设备编号查找，IP 不是设备身份，也不能覆盖台账。
- **REQ-CLI-07｜已确认**：接入方至少每一分钟调用一次状态上报 API；平台按最后一次有效状态上报的服务端接收时间计算未上报时长，超过五分钟没有新的有效上报时显示“状态未知”，不据此断言电脑断网。
- **REQ-CLI-08｜已确认**：平台向接入方提供版本化的标准接口文档，说明调用场景、请求与回执、示例、错误语义和接入验收要求；具体接口结构见详细设计第 8 节，调用示例见厂家接入文档，验证方法见架构测试与验收要求。

## 6. 推送、批量更新与回退需求

- **REQ-UPD-01｜已确认**：网页按钮和对外管理 API 都支持创建指定受管实例的目标版本任务，进入同一任务链；平台记录软件、目标版本、目标实例、发起人和回执结果。接入方通过接入 API 领取任务并提交结果。同一实例已有未完成任务或不满足目标版本条件时，该对象不创建新任务；批量请求中的合格实例继续创建，不合格对象逐项列出原因，不计入安装失败。
- **REQ-UPD-02｜已确认**：平台支持选择一批受管实例，并将大批量更新任务按可配置批次逐步提供给接入方领取。
- **REQ-UPD-03｜已确认**：服务端配置文件提供默认允许开始时间和最晚开始时间；发布人另选时段时以其选择为准。平台通过任务 API 提供本次执行时段，接入方可提前查询和下载，开始安装前须通过 API 核对是否允许执行。错过时段后等待重新安排；已经获准开始的任务在时段结束后仍可提交结果，平台不得直接标记为中止。接入方负责本机执行和实际结果上报；任务创建、下载完成或获准开始均不等于已安装。
- **REQ-UPD-04｜已确认**：平台能查看每批及每个受管实例的等待状态，以及接入方上报的下载、安装、成功、失败和回退结果；支持暂停未执行任务、定位失败对象和受控重试。达到可配置失败阈值时自动暂停尚未开放的后续批次，人员检查后可继续。本批部分实例超过配置的等待时间仍未返回结果时，也暂停后续批次；未回执不算安装成功或失败，须独立展示。人员处理或暂缓未完成对象后可继续；暂缓不代表现场执行结束。已获准安装但长期未回执的任务，在人员现场核实已无安装执行后，有权管理员可关闭跟踪；平台记录人员、原因与核实说明，保留“结果未知”，释放该实例以便安排后续任务，不计作安装成功或失败。
- **REQ-UPD-05｜已确认**：平台支持只对选定的部分实例创建指向可用历史版本的回退任务；其他实例不受影响。接入方须声明可回退范围及数据库兼容性；未确认兼容或已声明不兼容的历史版本不得成为回退任务目标，本机回退由接入方执行并上报。
- **REQ-UPD-06｜已确认**：更新与回退不得覆盖、重置或丢失本机数据库、日志及其他必须保留的现场数据。接入方负责本机数据保护，并提供数据位置、升级与回退行为说明及现场验收结果；平台保存相关任务与回执，不能仅凭 API 成功回执宣称现场数据安全。
- **REQ-UPD-07｜已确认**：批次大小、结果等待时限、默认执行时段和自动失败暂停阈值须可配置。失败阈值按当前批明确失败的实例数量 N 配置，重复回执不重复计数；不合格目标和未回执对象不计入明确失败。具体数值作为部署配置和架构验收输入，不在缺少现场数据时写死。接入方须为不能直接回退的数据库变更提供现场数据恢复方案。
- **REQ-UPD-08｜已确认**：接入方恢复 API 访问后仍可领取有效任务；平台对重复领取和重复回执作幂等处理，不得重复创建任务或错误推进状态。本机避免重复安装由接入方保证。人工关闭后的迟到回执仍归原任务及原执行记录，不能推进后续任务或把人工关闭改写成当时已确认成功。

## 7. 厂区、容量与质量要求

- **REQ-NFR-01｜已确认**：隔离厂区各部署独立服务，并在本厂内完成上传、发布、接入 API 调用和包分发；不能把厂区之间实时互通当成正常运行前提。
- **REQ-NFR-02｜已确认**：单厂以五万台设备、十万个受管软件实例为首期设计与压测基准。每分钟状态上报、版本查询、人员查询、任务领取和批量下载均须有容量和故障验收，不能只验证少量演示实例。
- **REQ-NFR-03｜已确认**：人员、外部系统和受管实例的权限彼此隔离；安装包下载、任务领取和状态上报须追溯到各自授权主体，不能用全厂共享凭据代表不同实例。
- **REQ-NFR-04｜已确认**：平台提供安装包完整性校验信息并验证所存安装包；接入方下载后按接入文档核对。错误包、丢失包或网络中断不能被平台记录为安装成功。
- **REQ-NFR-05｜已确认**：各厂包大小和现场可用带宽尚无数据，不承诺固定的全量下载完成时间。架构验收前须测量这两项，并据此确定批量下载及失败恢复的可验收完成时间。
- **REQ-NFR-06｜已确认**：隔离厂区保持独立台账、身份、包副本和更新事实；厂间不相互同步。各厂可显式绑定能通过 HTTPS 访问的 GitLab 正式来源，沿用源 Tag 版本；未绑定软件人工上传并按本厂规则编号。GitLab 不可达时恢复同步工作，已在本地就绪的包继续按本地权限供给；离线导入、Webhook 和 Runner 直推另批设计。

## 8. 首轮验收场景

以下场景用于检验需求是否覆盖真实操作；详细验证方法及证据要求见[架构测试与验收要求](./架构测试与验收要求.md)，本节不是实际执行结果。

1. GitLab 绑定软件的受保护正式 Tag 经核验和双副本后直接 Formal，无本地测试/发布操作且不自动投放；既有人工软件从网页和管理 API 上传时均由本厂平台生成三段版本号；不符合平台规则的自报版本号被拒绝。版本先进入测试视图，两页均显示更新内容并提供可用包下载，原 EXE 内部版本不参与平台编号。
2. 测试人员下载测试包并在一台设备安装；平台记录下载工号与时间。缺少该测试版本的实例上报时不能转正式；有上报后，具备该软件权限的人员填写测试通过原因和结论、手动发布，平台记录发布工号与时间，不要求独立测试记录或单独运行证明。
3. 最新可用正式版成为日常更新目标，明确选定的可用历史正式版可用于部分更新或回退；停用版本不能再下载或下发，包文件清理后其版本与操作历史仍可查询。
4. 接入方按每分钟一次上报版本与状态；网页显示上报 IP、厂区/工序/设备、最后上报时间和未上报时长。超过五分钟未上报时显示状态未知，不把未上报当作软件已停止。
5. 管理员按软件及已有设备映射范围开通受限接入授权，实例引用平台已有设备通过 API 登记；重复登记不重复占用名额，超过数量或有效期不得新增登记。不同受管实例使用独立接入身份和凭据；无权实例不能领取其他实例的任务或下载其无权访问的包。人员与外部管理 API 的软件范围和操作权限同样受到限制。
6. 网页和管理 API 均能创建批量任务，合格对象继续、不合格对象逐项列出原因。配置文件默认时段与发布人所选时段正确生效；错过最晚开始时间的实例等待重新安排，已获准开始的任务仍可回报结果。当前批明确失败达到 N 个实例，或未回执超过等待时限时，后续批次自动暂停；人员可定位原因并受控继续。重复领取和回执不改变已完成结果，未回执不被计作安装失败。
7. 只为选定实例创建回退任务，不影响其他实例；兼容性未确认或数据库不兼容的目标版本被拒绝。接入方现场验收更新、失败恢复和回退后数据库、日志仍完整可用，平台不以 API 回执代替现场验收。
8. 包被篡改、丢失或下载中断时，平台不得仅据下载记录标记安装成功；单厂按五万台设备、十万个受管实例验证上报、查询、任务领取、分批下载和恢复。下载完成时间根据实测包大小与可用带宽确定。
9. 已获准安装但长期未回执时，有权管理员填写现场核实说明和关闭原因后结束任务跟踪；平台保留结果未知及人员、时间，允许重新安排该实例。原任务的迟到回执可追溯，但不改变新任务状态，也不计作人工关闭时已经确认的成功或失败。
10. 在本平台维护工序、设备和软件映射；按现场层级查询同设备的上位机、视觉实例，软件共用版本库、实例保留各自安装履历。错误设备映射登记被拒绝且不占名额；无权软件不进入详情或汇总。设备名称含期别时不增加树层级，文档虚构值不进入真实台账。
11. 在统一工作台从工序看设备、从设备看软件、从软件看全部授权关联机台；同一设备内两台工控机及两个 PLC 的软件位置按需展开，任务进度和控制可从原对象进入；自动编号、上下文添加及旧归属补充不改变既有身份。按角色切换后，列表、数量、动作及目标均只包含有权范围。
12. PLC 上传仅进入 Test，人员填写验证与结论后转 Formal；另一台 PLC 的历史和人工确认使用版本不变，上传身份不能发布。GitLab 正式导入不需要本地测试，导入后仍由人员明确创建更新任务。
