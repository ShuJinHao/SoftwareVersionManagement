# 制造业软件版本管控平台架构测试与验收要求

> 状态：已审阅；本次版本与安装包验证记录修订待复核。本文定义验证方法，不是测试报告；本文 52 项正式验收用例尚未逐项执行，依赖现场输入的项目仍待条件确认。人员管理 API/网页、双节点会话、幂等及基础框架的局部验证见[软件框架设计](./软件框架设计.md)第 11 节，不据此将本文用例批量标为通过。文档审阅通过不等于系统、容量或厂家现场验收通过。

## 1. 范围、依据与责任

### 1.1 验证范围与规则来源

验收对象是各隔离厂区独立部署的 Linux .NET 8 服务端、网页管理端、管理 API、接入 API、包分发及接入文档。平台负责本地工序/设备台账、软件分类与映射、包、任务、状态和回执；上位机/视觉接入方负责本机安装、回退、避免重复安装及现场数据保护。PLC 只验证后续备份归档边界，具体功能待确认。协议模拟器的成功回执不能证明现场软件已安装，更不能代替数据库和日志验收。

本文件只规定如何验证现有规则，不增加 API、业务状态或客户端内部实现要求。发生规则歧义时，记录受影响用例和依据，先澄清设计，再执行及判定；不得由测试人员自行发明另一套规则。

| [总体架构](./总体架构.md)，第 1～7 节 | 系统边界、厂区部署、容量预算和故障边界 |

| [厂家接入文档](./厂家接入文档.md)，第 2～9 节 | 接入操作示例、异常恢复、厂家材料与接入自检 |

### 1.2 责任分工

| 责任方简称 | 主责与交付 |
|---|---|
| 平台研发 | 解释实现及模块边界，提供可追溯构建、配置和受控故障注入条件，修复平台缺陷 |
| 平台验证 | 执行功能、接口、权限、一致性与容量验证，整理请求、数据库事实和指标证据 |
| 厂区运维 | 确认服务器、网络、入口、数据库和包节点条件；实施获授权的故障与恢复演练并保存操作证据 |
| 接入方 | 按同一契约实现自研或厂家客户端，执行本机更新、失败恢复、回退和数据保护验证，提交真实材料 |
| 业务验收人 | 确认业务流程、现场关键数据及可用性；与厂区运维、平台负责人确认性能和恢复目标，审查结论 |

同一人可以承担获授权的多种产品操作，不设置强制不同人员上传、测试确认和发布的流程。表中责任分工是验收执行职责，不新增产品审批页面或发布审批步骤。每次执行记录具体执行人和验收人；平台与接入方的责任不能互相替代。

## 2. 验证环境与待确认输入

### 2.1 环境和公共数据

| 标识 | 用途和最低说明要求 |
|---|---|
| ENV-FUNC | 隔离的功能环境，使用真实数据库和文件存储验证事务与文件行为；网页和 API 指向同一组业务服务。纯桩件结果不能代替一致性验证 |
| ENV-HA | 与拟交付部署方式相符的冗余入口、多 API、可切换数据库和不同故障域包副本环境；记录实际物理拓扑、同步与故障切换方式 |
| ENV-CAP | 单厂 5 万个设备标识、10 万个独立受管实例的容量环境；每实例有独立凭据和上报流，负载发生器资源单独监控。逻辑模拟规模与真实现场设备数分别注明 |
| ENV-SITE | 接入方支持范围内、经授权的现场验收环境；使用代表性的目标操作系统、软件、数据库、数据量和日志。平台服务端技术栈不限制客户端语言 |

公共数据使用明确虚构的本厂工序、设备编号/名称及软件映射，覆盖上位机、视觉分类、不同资产/软件权限的主体、测试/正式/停用版本和不同数据库兼容性实例。包含同 IP 不同实例、同设备多软件、同软件多设备、已映射未登记、从未上报、无 IP 和有未完成任务的对象；无工序/无设备映射只作为登记拒绝数据，不作为合法位置空缺。聊天中的厂区和设备举例不得成为实际台账或默认值。

容量环境须记录设备与实例的对应关系、各软件实例分布和单软件最大规模，不把 10 万实例分散到大量小软件后声称已验证一个大型软件的批量投放。版本、任务、凭据和字段示例使用虚构数据；客户端现场数据按授权脱敏。

功能边界用例可使用专用配置值和受控服务端时钟，执行前记录实值。用例中的 `B`、`N`、`W` 分别引用已有批次大小、失败数量和等待时限配置，不给生产配置新增默认数值。需要验证达到阈值后仍有当前批对象时，选择 `B > N` 的测试数据即可，这不是新增产品配置限制。

### 2.2 验收前待确认输入

本节是六份文档的现场待确认输入统一入口，以下均为**待条件确认**。其他文档引用 IN 编号，不另维护同一参数的生产取值。先记录测量结果、拟定目标及确认人，再执行受影响的正式验收；探索性测量可以用于定目标，但不能事后把测得结果直接当作通过阈值。

| 输入编号 | 待确认项 | 测量或确认方法与责任 | 影响范围 |
|---|---|---|---|
| IN-01 | 服务器规格、节点数、故障域、存储类型、数据库同步及切换方案 | 厂区运维提供 CPU、内存、磁盘、网络、拓扑及配置清单；平台负责人确认与拟交付环境的差异 | 架构部署、全部恢复及容量用例 |
| IN-02 | 包大小分布、最大包、投放包组合、保留量 | 接入方提供代表性包，记录字节数和摘要；平台与业务验收人确定代表组合 | 包分发、文件恢复、备份和并发下载 |
| IN-03 | 各网络路径可用带宽及竞争流量 | 运维测量入口、包节点、客户端所在网段的持续有效吞吐，记录时段、方向及其他业务流量 | 下载完成时间和恢复重连场景 |
| IN-04 | 批次大小、失败阈值、等待时限、默认执行时段及轮询间隔 | 结合现场维护窗口和代表性安装过程确认；记录配置来源及每次投放参数快照 | 任务、混合负载和批量容量 |
| IN-05 | 查询比例、并发人员、各软件规模、突发与重连分布 | 根据预期业务和现场日志确认负载模型；包含单软件集中、整分钟集中报告及错峰报告 | 五项容量用例 |
| IN-06 | 预热、稳态、持续运行、故障保持、恢复观察时长及采样间隔 | 验证与运维提出能观察积压、资源增长、租约与超时的时长，由验收人确认 | 容量、恢复、资源稳定性 |
| IN-07 | 请求延迟分位数阈值、错误率、积压上限及消退时间 | 按接口类型和正常/故障阶段分别约定；明确哪些拒绝是预期行为，限流如何计入 | 性能通过判定 |
| IN-08 | 批量任务准备、包下载及恢复后的完成时间目标 | 用 IN-01～06 的实测条件和代表负载估算，再通过预演确认；目标与条件绑定 | 批量任务、下载和重连验收 |
| IN-09 | 各故障恢复时间目标、可接受恢复点、备份频率与保留期 | 运维、平台负责人和业务验收人按数据库、文件、身份材料分别确认 RTO/RPO；标明是否包含人工处置时间 | 数据库切换、节点恢复和备份恢复 |
| IN-10 | 厂家支持矩阵、关键数据、正常迁移及日志连续性标准 | 接入方列出数据位置、数据库结构、业务不变量、预期新增写入及恢复方案，业务验收人确认抽样和完整核对范围 | 三项现场数据用例及回退 |
| IN-11 | 请求/分页/包限制、队列上限、连接池、租约、健康检查和时钟误差 | 保存拟用配置；运维测量节点时钟偏差，验证负责人确定边界观测精度与故障检测触发方式 | 边界、并发、故障、容量测量 |

5 万设备、10 万实例、至少每分钟一次报告是已确认基准；约 `100000 / 60 ≈ 1667` 次/秒仅是均匀分布下的报告请求平均预算。它不是已测吞吐，不包含查询、鉴权、领取、回执或重试，也不能代表整分钟突发峰值。无包大小与带宽数据时不承诺全量下载完成时间。

## 3. 用例记录、证据与判定

### 3.1 统一记录

每个用例以下面的固定字段编写：标题中的用例编号、对应需求、责任方、前置条件、操作步骤、预期结果、证据要求。执行时补充运行编号、用例修订、实际结果、状态、偏差/缺陷及执行人与验收人；多组分支逐组记录，不能只运行成功分支便将整个用例标为通过。

同一次验证的证据清单应包含：七份设计/接入/验收文档及项目初始化的文件摘要或修订标识、被测服务和客户端产物标识、环境拓扑、完整配置快照及其摘要、数据准备方式、负载工具版本与随机种子（如使用）、开始结束时间、时钟偏差、故障注入与恢复时间线、证据位置及摘要。执行记录在后续实际验证时产生，本批不创建运行报告或证据空壳。

### 3.2 证据分类

| 标识 | 最少保留内容 |
|---|---|
| EV-DOC | 需求/接口/页面/验收依据的修订标识、规则追溯、虚构示例标记、PLC 待确认边界及与实现状态的差异；不代替运行证据 |
| EV-HTTP | 脱敏请求与响应、方法及路径、服务端时间、状态码、错误码、traceId、幂等键和业务标识；秘密、密码、Cookie 和授权头均脱敏 |
| EV-DB | 变更前后相关事实、唯一约束/索引、任务与执行记录、实例占用约束、计数和审计的只读查询结果；包含关键事务或提交失败点的关联证据 |
| EV-FILE | 包清单、字节数、SHA-256、各副本及暂存实际状态、文件工作、下载会话和传输结果；证据与业务 ID 关联 |
| EV-UI | 页面操作、筛选条件、时间和结果截图或录像；同时关联 API/数据库事实，不能仅用截图证明事务提交 |
| EV-OPS | 拓扑与配置、节点/进程代次、租约、数据库切换、健康检查、备份及恢复时间线；记录注入位置、恢复动作和操作者 |
| EV-METRIC | 计划与实际请求量、延迟分布、错误分类、重试、积压、资源和锁等待、下载吞吐及恢复时间的原始时序数据和计算方法 |
| EV-SITE | 现场软件/包/任务/执行标识、更新前后关键数据清单与核对结果、业务读写检查、日志连续性、异常恢复和接入方/业务验收人确认 |

对持续变化的数据库和日志，应核对关键记录、业务不变量、允许的迁移和新增日志；不能简单要求运行中数据库文件的二进制摘要始终不变。反之，API 成功、数据库行数相同或文件仍存在，也不能独自证明关键数据完整、可读和业务可用。

### 3.3 判定状态

| 状态 | 判定条件 |
|---|---|
| 待条件确认 | 缺环境、授权的故障条件、数据、厂家支持范围或性能/恢复目标；列出具体 IN 编号及责任人 |
| 待执行 | 条件已齐备，尚未执行，或缺少足以判定的执行证据；说明待补证据，不推定通过 |
| 通过 | 所有适用分支满足预期，证据可关联复核；涉及定量目标时同时满足事先确认的目标 |
| 失败 | 已观察到与需求/契约相违背的结果，或未达到已确认目标；保留缺陷和复验范围 |

本稿所有用例初始均为“待执行”，其中依赖第 2.2 节未落实输入的用例为“待条件确认”。环境缺失不能记作通过；不得用平均成功率掩盖越权、错误安装许可、重复推进任务、审计缺失或现场数据损坏。发现失败后不能仅因其他证据缺失把它改回待执行。

## 4. 架构与一致性

### AT-ARC-01｜模块数据归属和依赖方向

- **对应需求**：REQ-AUTH-02、REQ-UPD-08、REQ-NFR-02。依据：模块设计第 1～5 节，详细设计第 2、7、10.2 节。
- **责任方**：平台研发提供实现与依赖证据，平台验证主责核对。
- **前置条件**：实现可供检查，具有模块、应用用例、数据映射及内部契约清单；本用例在后续开发完成后执行。
- **操作步骤**：1. 逐项定位六个模块实体的写入入口；2. 跟踪上传发布、批量投放、回退和清理四条调用链；3. 检查网页、管理 API、接入 API、后台任务是否经过共同用例及契约；4. 核对持久化写入和模块依赖图。
- **预期结果**：数据修改由所属模块负责，应用用例协调，无相互写表或循环回调；包运行会话与不可变下载审计分别按既定归属管理；组合查询不形成第二套可修改的业务事实。四条流程与契约责任一一对应。
- **证据要求**：实现位置、依赖图及实体到写入者清单；EV-DB 和四条调用链的关联记录。

### AT-ARC-02｜业务与审计共同提交

- **对应需求**：REQ-AUTH-02、REQ-REL-06、REQ-UPD-08。依据：模块设计第 5 节，详细设计第 7.1 节。
- **责任方**：平台验证主责，平台研发提供受控故障点。
- **前置条件**：ENV-FUNC；分别准备上传登记、发布、投放、暂停、终态回执及人工关闭操作。
- **操作步骤**：1. 对每种操作在业务写入后、提交前使必须审计写入失败；2. 恢复后读取业务、审计及幂等结果；3. 再模拟提交成功但响应丢失，按原身份和幂等方式重试；4. 对拒绝的操作查询拒绝审计与业务对象。
- **预期结果**：必须共同提交的业务与审计全成或全败；失败不缓存成功结果。已提交请求重放不重复业务变更或原业务审计；拒绝不产生目标业务变更，其独立拒绝记录不能冒充业务成功。关闭和终态操作不得留下孤立实例占用或错误释放其他任务。
- **证据要求**：EV-HTTP、EV-DB；逐操作保留提交边界、失败注入位置、关联 ID 和前后事实。

### AT-ARC-03｜跨 API 节点的同一事实与唯一约束

- **对应需求**：REQ-AUTH-04、REQ-CLI-02、REQ-UPD-08、REQ-NFR-02。依据：详细设计第 2、3、5、7.1 节。
- **责任方**：平台验证主责，厂区运维协作。
- **前置条件**：ENV-HA；至少可将同一逻辑操作分发至不同 API 节点。
- **操作步骤**：1. 在不同节点交替登录/鉴权、登记、上报、领取及回执；2. 并发向同一实例创建任务和领取同一任务；3. 检查数据库唯一约束及实际冲突结果；4. 多次发送不变周期快照并检查事实留存方式。
- **预期结果**：权限、会话撤销、身份、任务及快照不依赖单节点内存；同一实例最多一个未结束任务，同一任务只有一个执行记录；重复操作不新增占用或许可。周期快照更新与版本变化、测试证据和任务历史的保留分别符合设计，不要求永久保存每次相同报告。
- **证据要求**：EV-HTTP、EV-DB、EV-OPS；标明处理节点、唯一约束及并发操作顺序。

### AT-ARC-04｜包传输路径和受控访问

- **对应需求**：REQ-CLI-04、REQ-NFR-03、REQ-NFR-04。依据：总体架构第 2、5 节，详细设计第 7.2、8.6 节。
- **责任方**：平台验证主责，厂区运维与平台研发协作。
- **前置条件**：ENV-HA；有效包、有效及无权人员/系统/实例身份；入口和内部服务访问证据可读取。
- **操作步骤**：1. 各类授权主体经既定下载路径 GET、HEAD 和 Range 请求；2. 去掉凭据或改用无权身份重试；3. 尝试直接访问暂存、存储路径和服务器内部接口，在公开请求伪造内部主体/节点头，或使用某节点采集身份提交其他节点的结束记录；4. 关联入口、API 鉴权与包节点流量。
- **预期结果**：包字节由 Nginx/包节点服务，API 执行授权而非转发包字节；未授权请求不能取得包，内部路径或伪造头不能绕过入口、冒充主体或改写其他节点传输事实。HEAD 不记为包已完整下载。Nginx 鉴权失败按详细设计的传输语义处理，不要求其返回与业务 API 完全相同的 JSON 错误体。
- **证据要求**：EV-HTTP、EV-FILE、EV-OPS；保留授权主体、下载会话、传输日志和节点流量，证明路径及审计可关联。

### AT-ARC-05｜隔离厂区独立运行

- **对应需求**：REQ-AUTH-04、REQ-REL-07、REQ-NFR-01、REQ-NFR-06、REQ-ASSET-01。依据：总体架构第 1～3 节，详细设计第 1.1 节。
- **责任方**：厂区运维与平台验证主责，业务验收人确认业务流程。
- **前置条件**：两套相互隔离的代表环境，分别配置本厂身份、数据库、入口和包存储；不接入现有 Cloud 身份服务。
- **操作步骤**：1. 在两厂分别维护工序/设备台账及软件映射、开通账号、登记同名软件并上传同一文件；2. 在一厂修改台账和增加版本，另一厂保持自己的记录；3. 禁止厂际连通，分别完成测试上报、人工发布和任务查询；4. 用一厂凭据访问另一厂。
- **预期结果**：每厂独立维护台账、映射、版本编号、存包和授权；一厂操作不改写另一厂状态，正常流程不依赖厂际实时访问或 Cloud。跨厂凭据无效，不需要同步、导出或导入接口完成本地业务。
- **证据要求**：EV-HTTP、EV-DB、EV-FILE、EV-OPS；两厂配置与网络隔离证据，分别关联版本和任务。

## 5. 身份与接口

### AT-SEC-01｜软件范围、操作权限与人员专属操作

- **对应需求**：REQ-AUTH-01、REQ-AUTH-03、REQ-NFR-03。依据：详细设计第 3.1、8、9 节。
- **责任方**：平台验证主责，业务验收人确认网页流程。
- **前置条件**：ENV-FUNC；按软件和操作建立有权、只读、无权人员与管理系统；一名人员同时拥有上传、发布和推送权限。
- **操作步骤**：1. 逐项从网页和对应管理 API 执行读取、上传、下载、发布、推送、回退、控制及清理；2. 每项撤销对应软件或操作权限后重试；3. 同一人员完成上传、发布、推送；4. 用系统凭据尝试创建登记/恢复授权、人工发布和人工关闭，尝试提交伪造工号。
- **预期结果**：全部入口使用一致的软件及操作限制；无权调用不变更业务，返回契约规定的拒绝。人员专属操作不能由管理系统代替；工号来自会话，未知请求字段不能伪造操作者。同一获授权人员可以完成多项操作，无额外测试审批步骤。
- **证据要求**：权限矩阵；EV-HTTP、EV-UI、EV-DB，包含真实授权主体与审计快照。

### AT-SEC-02｜实例与外部系统身份隔离

- **对应需求**：REQ-AUTH-04、REQ-CLI-05、REQ-NFR-03。依据：详细设计第 3、8.2、8.5、8.6 节。
- **责任方**：平台验证主责，接入方提供独立身份调用记录。
- **前置条件**：两个管理系统及同软件/异软件实例，各有独立凭据；包含同 IP 和同设备多实例。
- **操作步骤**：1. 各主体查询自身允许资源；2. 替换 instanceId、taskId、attemptId 访问其他实例任务或写其事实，并比较下载同软件可用包与异软件包；3. 使用实例凭据调用管理接口，使用登记授权调用日常接口；4. 分别吊销一份凭据并验证其他主体。
- **预期结果**：任务与上报按实例隔离，实例下载按所属软件及版本可用性授权，不额外要求本软件可用包已有投放任务；越权资源按详细设计返回拒绝或不可见资源结果。软件及实例绑定不可由请求改写，没有全厂共享日常凭据；同 IP 不合并实例，单独吊销不撤销其他主体，自研与厂家限制相同。
- **证据要求**：EV-HTTP、EV-DB；身份到软件、实例及资源范围对照，全部秘密脱敏。

### AT-SEC-03｜受限登记、重复与并发名额

- **对应需求**：REQ-AUTH-04、REQ-UPD-08、REQ-ASSET-03。依据：详细设计第 3.2、8.2 节，厂家接入文档第 4.1 节。
- **责任方**：平台验证主责，接入方验证本地标识保存与重试。
- **前置条件**：受限软件、已有设备范围、有效期与名额的登记授权；平台已有工序/设备/软件映射、deviceId，接入方保存的 installationKey 和随机秘密。
- **操作步骤**：1. 正常登记并模拟响应丢失后原样重试；2. 并发重复登记及不同实例竞争最后名额；3. 更换绑定字段或秘密重试同一安装标识；4. 到期、撤销、额度耗尽后分别尝试新增；5. 对到期、耗尽及撤销授权分别用原键重放此前成功且原凭据仍有效的完全相同登记，再验证已吊销凭据场景。
- **预期结果**：成功身份、独立凭据、名额和审计共同提交；同一登记仅耗用一个名额，超额不能新增。冲突返回既定错误，不重绑身份；到期、耗尽或撤销后只可按原键/原请求及有效原秘密找回原成功结果，不能新增或复活吊销凭据。登记响应不返回秘密。
- **证据要求**：EV-HTTP、EV-DB；并发次序、名额前后值、原请求与重放结果，以及接入方持久化标识的脱敏说明。

### AT-SEC-04｜凭据吊销、恢复与旧报告流失效

- **对应需求**：REQ-AUTH-04、REQ-UPD-08。依据：详细设计第 3.2、5.1、8.2、8.5 节，厂家接入文档第 6.2 节。
- **责任方**：平台验证与接入方主责，厂区运维协作跨节点检查。
- **前置条件**：已有任务和历史的实例；有权管理员发给该实例的一次性恢复授权。
- **操作步骤**：1. 撤销原凭据，跨 API 节点尝试使用；2. 用恢复授权及新秘密恢复，模拟响应丢失重放；3. 尝试恢复其他实例或二次生成不同凭据；4. 建立新上报流，发送旧凭据/旧流报告，再查询原任务和历史。
- **预期结果**：恢复仍绑定原实例，原任务和历史保留；原凭据失效，恢复授权不能被消费出多个身份。重复同请求返回原恢复结果；新报告流生效后旧流不能覆盖状态，跨节点结果一致。
- **证据要求**：EV-HTTP、EV-DB、EV-OPS；凭据 ID、授权消费、streamEpoch、实例及历史关联，秘密不入证据正文。

### AT-SEC-05｜会话、传输及敏感信息保护

- **对应需求**：REQ-AUTH-01、REQ-AUTH-02、REQ-NFR-03。依据：总体架构第 5 节，详细设计第 3.1、8.1、8.2 节。
- **责任方**：平台验证主责，平台研发与厂区运维协作。
- **前置条件**：人员会话、首次改密账号、管理和实例凭据；部署的 TLS、共享会话撤销和密钥保护配置可审查。
- **操作步骤**：1. 验证 Cookie、CSRF 和首次改密限制，从网页/API 管理人员；2. 退出、改密、重置、停用后跨节点重试旧会话，再启用；3. 编辑四项厂级及真实软件范围授权，验证逐项选择、候选基本字段、错误软件/范围/操作拒绝及当前撤权，未修改条目完整保留；4. 检查传输、内部入口、正常/异常/重放时日志、审计、结果、响应及浏览器存储；5. 两管理员并发自停用/撤权，尝试删除最后管理员；6. 注入审计/保存失败或取消，核对账号、授权、会话、revision 与结果共同回滚。
- **预期结果**：仅首次改密完成且当前有 identity.manage 的人员可管理；工号唯一不可改，无历史主体删除入口。新建/重置须改密，旧会话失效且启用不恢复；至少保留一个启用人员管理员。四项厂级和软件目录操作按真实软件维护，候选只提供授权基础信息，不自动勾选全部操作；软件创建只授予三项初始权限，未实现功能仍关闭。会话、CSRF、TLS、回滚和真实操作人审计符合设计；无秘密输出或浏览器持久化。
- **证据要求**：EV-HTTP、EV-UI、EV-DB、EV-OPS；安全配置、双节点/并发时序、共同回滚和脱敏检查，禁止把原始秘密作为附件交付。

### AT-API-01｜字段、错误和异步响应契约

- **对应需求**：REQ-CLI-04、REQ-CLI-08、REQ-NFR-03。依据：详细设计第 8 节。
- **责任方**：平台验证主责，接入方协作验证可理解的错误处理。
- **前置条件**：以详细设计第 8 节生成接口核对清单；各接口至少有正常输入和适用的无权/不存在/非法状态输入。
- **操作步骤**：1. 核对方法、路径、必填/可选字段、UUID、时间、枚举大小写及 JSON 格式；2. 逐项检查缺字段、未知写字段、大小超限和状态冲突；3. 检查错误体、traceId、retryable 和适用的 Retry-After；4. 对异步上传、选择集、投放及控制工作沿返回标识查询最终结果。
- **预期结果**：实现逐项对应既有契约，没有自行新增字段或路径；业务 API 的状态码及错误结构符合第 8.7 节。202 表示工作已受理，不表示包可用、所有目标准入或安装成功；传输接口采用第 8.6 节规定的响应语义。
- **证据要求**：接口到输入分支的核对清单、EV-HTTP；保留异步请求与最终工作结果关联。

### AT-API-02｜幂等、并发修改与当前授权

- **对应需求**：REQ-AUTH-02、REQ-REL-02、REQ-UPD-08、REQ-ASSET-03。依据：详细设计第 7.1、8.1 节。
- **责任方**：平台验证主责，平台研发协作提交边界验证。
- **前置条件**：具有幂等键的写接口和需要 expectedRevision 的修改接口；另列不采用通用幂等键的报告、回执、内容上传和分块接口。
- **操作步骤**：1. 同主体以同键并发和跨节点重放语义相同的请求，包括 JSON 字段顺序变化；2. 同键改业务内容；3. 不同请求并发使用旧 revision；4. 成功后以原键及原 revision 重放；5. 撤销当前权限后再次重放成功请求；6. 各例外接口按自己的自然键或序号执行重复调用；7. 人员网页提交在数据库成功后丢失响应，检查不自动再发，由人员手动用原正文/原键核实；模拟提交确认丢失并在新 Scope 核对当前授权及原结果。
- **预期结果**：相同业务请求只产生一次逻辑变更；改内容冲突，陈旧并发修改拒绝。合法成功重放先找回提交结果，不因原 revision 已变而误判失败；当前身份无权时不能从幂等缓存绕过鉴权。回滚操作不缓存成功，各例外接口采用自己的去重契约。人员网页保留待核实的原请求/原键，禁止自动换键、重复点击或静默重发；修订冲突加载最新详情后由人员决定。提交未知不自动重执行，重新授权失败不返回成功结果。
- **证据要求**：EV-HTTP、EV-DB；记录键、请求摘要、revision、授权变化及业务/审计行数和关联。

### AT-API-03｜分页、目标分块与封存

- **对应需求**：REQ-CLI-03、REQ-UPD-02、REQ-NFR-02。依据：详细设计第 6.1、8.1、8.4、10.1 节。
- **责任方**：平台验证主责。
- **前置条件**：多页数据及可在查询期间变化的实例集合；显式选择与筛选选择均可使用。
- **操作步骤**：1. 在静态集合逐页核对数据，再在集合变化时观察既定游标语义；2. 篡改游标、换主体/部署/筛选/页长、使用过期游标或超过分页上限，人员按工号/ID 核对固定排序、默认 50 与最大 200；3. 重复/冲突上传目标块，漏块或错报去重数后封存；4. 筛选物化期间改变实例状态并中断工作；5. 封存后再改变筛选匹配情况并执行准入；6. 人员网页检查空集合、读取失败、权限撤销及无管理权状态。
- **预期结果**：分页遵守范围、排序和限制，不能越权或绕过边界；普通动态分页不被误当成不可变目标快照。显式块完整、去重数一致才可封存；筛选集合按设计的同一 MVCC 视图物化，未完成不能使用。封存后成员不漂移，准入仍重新核对实际资格。
- **证据要求**：EV-HTTP、EV-DB；游标条件、逐块清单、封存成员摘要、物化中断与恢复事实。

### AT-API-04｜按接入文档走通同一套协议

- **对应需求**：REQ-CLI-04、REQ-CLI-05、REQ-CLI-08。依据：详细设计第 8 节，厂家接入文档第 2～9 节。
- **责任方**：接入方主责调用，平台验证核对；自研与厂家代表各执行一组。
- **前置条件**：已实现服务及有效接入信息；将文档示例占位符替换为隔离环境真实标识，保留调用方关联记录。
- **操作步骤**：1. 按登记、建立流、报告、版本/任务查询、领取、下载校验、申请开始、回执顺序调用；2. 中途重启调用方并依靠已保存标识续接；3. 按文档处理可重试、等待时段、暂停和人工处置分支；4. 需要管理系统的接入方另走上传、选择集、投放及结果查询流程。
- **预期结果**：路径、字段、状态和错误能与详细设计及示例逐项对照，标识连续且可恢复；自研与厂家没有不同私有协议或客户端语言要求。系统凭据不代替人员发布或人工关闭；文档可操作性得到实际调用证据支持。
- **证据要求**：EV-HTTP，接入方保存标识及重试决策清单；该协议验证结论不得标成现场安装或数据保护验收通过。

## 6. 版本、网页与实例状态

### AT-REL-01｜平台编号生成、拒绝与并发

- **对应需求**：REQ-REL-02、REQ-REL-03、REQ-REL-07、REQ-REL-08、REQ-ASSET-02。依据：详细设计第 4、8.3 节。
- **责任方**：平台验证主责，业务验收人确认网页提示。
- **前置条件**：空软件及已有不同版本的软件；网页与管理 API 均可操作。
- **操作步骤**：1. 分别从网页和 API 登记首版、Patch、Minor、Major；2. 提交不符的 expectedVersion、非法级别、缺失说明及自行增加的版本字段；3. 并发登记并检查最高已登记编号；4. 将已登记上传置为失败后再登记；5. 使用 EXE 内部版本与平台编号不同的包，检查发布后的编号。
- **预期结果**：首版和后续增量符合 REQ-REL-07，编号按数字段比较。预期冲突不分配新号；已登记后失败的编号保留且不回收。网页/API 不能改号或覆盖旧包，EXE 内部版本不参与编号；转正式保留原编号和包关联。
- **证据要求**：EV-HTTP、EV-UI、EV-DB；保留完整分配序列、冲突记录、变更级别和操作者时间。

### AT-REL-02｜上传校验、不可覆盖和副本就绪

- **对应需求**：REQ-REL-02、REQ-REL-03、REQ-REL-08、REQ-NFR-04。依据：详细设计第 4、7.2、8.3 节。
- **责任方**：平台验证主责，厂区运维协作文件核对。
- **前置条件**：ENV-FUNC/ENV-HA；正确包及大小或摘要错误的包，能控制复制和校验完成时点。
- **操作步骤**：1. 网页/API 登记相同类型发布信息并上传；2. 并发向同一上传标识写内容，提交不符字节，重传预期正确内容；3. 暂停校验或冗余复制后查询、下载和尝试发布；4. 达到副本条件后再次查询；5. 尝试改变已登记预期摘要或覆盖 Ready 包内容。
- **预期结果**：状态按详细设计流转，实际大小和摘要由服务器核对；副本未齐备不能开放测试下载或转正式，达到条件仅进入测试版，不自动正式。上传中断按整包重传处理；失败记录保留，重试只接受既定内容。已发布内容和关联不可悄悄替换。
- **证据要求**：EV-HTTP、EV-DB、EV-FILE；各副本独立大小/摘要、处理阶段、失败与重试关联及不可覆盖检查。

### AT-REL-03｜测试下载、版本上报与人工发布

- **对应需求**：REQ-AUTH-03、REQ-REL-04、REQ-REL-05、REQ-REL-06。依据：详细设计第 4、5.1、7.2、8.3、9 节。
- **责任方**：平台验证主责，接入方报告测试版本，业务验收人确认发布流程。
- **前置条件**：可下载测试版、同软件测试实例、有权发布人员及无权人员；准备不对应的证据。
- **操作步骤**：1. 人员下载测试包，分别观察 HEAD、GET、传输中断与完成记录；2. 在无测试上报、仅任务成功或错误版本/软件证据时尝试发布；3. 上报正确已安装测试版本，运行状态分别取 Stopped 或 Unknown；4. 缺少原因/结论及无权身份分别尝试；5. 有权人员填写原因与结论后转正式，同一人员可承担先前上传。6. 后续上报其他安装版本并超过五分钟后选择原历史证据；7. 两副本分别缺失、过期、修复中或无核对时间时尝试；8. 重放原键、修改原键正文、撤权后核实，并发发布/停用及失败/取消/提交确认丢失。
- **预期结果**：下载人员工号、时间和传输结果可追溯，HEAD 不伪造下载完成。必须引用对应测试版本上报，上传、下载或任务成功均不代替证据；有效测试上报不自动发布。人工提交符合条件即可发布，不额外要求 Running 证明或独立测试审批；工号与时间由平台记录。历史 Installed 证据不要求仍为当前快照或五分钟新鲜度；发布须包大小/摘要正确、两个固定节点副本健康且核对时间有效，事务只核验数据库事实。发布资料/固定证据引用/审计/结果共同提交、失败整体回滚；形成后不可改写，合法原键先于旧 revision，当前授权先于重放，提交未知只核实。
- **证据要求**：EV-HTTP、EV-UI、EV-DB、EV-FILE；下载、测试证据、发布原因/结论、人员工号和版本关联。

### AT-REL-04｜测试/正式视图、默认目标和历史

- **前置条件**：多软件、多测试/正式版本、停用版本及历史下载/发布记录；包含数字比较容易误排的版本序列。
- **操作步骤**：1. 切换软件及测试/正式页面，检查说明、状态和可用下载；2. 默认创建任务后再发布更高版本；3. 明确选择仍可用的历史正式版创建符合方向要求的任务；4. 停用版本后查询历史与默认可用目标；5. 对比任务结果与实例上报版本。6. 对比 1.0.2/1.0.10、后发布的较低编号、停用最高编号、单副本/全部不可供包；7. 查询软件目录、实例、设备汇总、客户端 context 与默认 Formal，撤销软件读取权限后复查。

### AT-STA-01｜安装/运行事实、报告顺序与证据留存

- **对应需求**：REQ-CLI-01、REQ-CLI-02、REQ-CLI-07、REQ-REL-06。依据：详细设计第 5.1、6.6、8.5 节。
- **责任方**：平台验证与接入方主责。
- **前置条件**：已登记实例、有当前报告流和可关联版本；准备未关联现场版本。
- **操作步骤**：1. 报告完整安装/运行/IP/数据库快照并更新版本；2. 重放同序号同内容、当前同序号不同内容、较小序号和旧流报告；3. 建立新流后并发提交旧流；4. 仅下载、领取或提交任务成功而不提供有效新快照；5. 上报未关联版本，随后更新为其他版本并查询测试证据。
- **预期结果**：安装时间、报告时间与服务端接收时间分别保存；新有效报告才推进快照和 lastAcceptedAt。重复、冲突、旧序号/旧流按设计处理，不覆盖新事实或刷新新鲜度；不要求已裁剪的旧报告逐份留存。任务成功不自动填入目标版本，未关联版本如实显示且不能作发布/兼容证据；应保留的测试及版本变化证据不因快照更新丢失。

### AT-STA-02｜每分钟报告和五分钟状态边界

- **对应需求**：REQ-CLI-02、REQ-CLI-07。依据：详细设计第 5.1、8.5、9 节。
- **责任方**：平台验证核对服务端边界，接入方验证周期调用。
- **前置条件**：ENV-FUNC；可重复控制或观测服务端时间，确认 IN-11 的误差；实例先无报告，随后持续每分钟至少报告一次。
- **操作步骤**：1. 查询从未报告实例；2. 记录一份新报告的 lastAcceptedAt，停止新报告；3. 在 300 秒之前、恰好 300 秒、严格超过 300 秒查询；4. 修改客户端 reportedAt 或重放旧请求；5. 恢复有效新报告。
- **预期结果**：从未报告显示尚未上报；恰好五分钟不越界，严格超过五分钟显示状态未知和未上报时长，仍能查最后报告值与时间，不显示为已确认停止或电脑断网。客户端时间和重复旧报告不能延后边界，新有效报告恢复新鲜度；接入方周期调用记录满足至少每分钟一次。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；记录边界所用服务端时间、精度和 reportSeq，不能仅凭人工等待“大约五分钟”判定。

- **责任方**：平台负责人及文档/业务审阅人；具体 PLC 功能验收须另行确认。

- **操作步骤**：1. 对照七份文档的 PLC 表述及实现状态；2. 对照 EXE/安装包及压缩容器的分类规则；3. 核对页面和 API 没有将未来 PLC 备份写为已支持的下装、安装回退或每分钟上报。
- **预期结果**：PLC 仅保留程序备份/压缩包归档方向，具体流程待确认、功能待实现；压缩扩展名不触发 PLC 行为，无虚构在线状态、任务或验收通过承诺。此边界核对不构成 PLC 备份功能验收。
- **证据要求**：EV-DOC；适用时增加 EV-UI/EV-HTTP，明确设计审阅、边界核对与功能运行验收的区别。

## 7. 任务、批次与部分回退

### AT-TSK-01｜批量准入、部分拒绝与准备恢复

- **对应需求**：REQ-UPD-01、REQ-UPD-02、REQ-UPD-08。依据：详细设计第 6.1、8.4、9 节。
- **责任方**：平台验证主责，业务验收人核对逐项反馈。
- **前置条件**：封存选择集混合合格、已有未结束任务、暂停实例、版本未知、目标相同及不满足回退条件对象；具备受控的授权/资格变化条件。
- **操作步骤**：1. 分别从网页/API 创建投放，查询 Preparing 及逐项处理结果；2. 在准备期间改变部分对象资格并重启工作者；3. 对全部不合格集合创建投放；4. 准备中执行取消或使全局版本条件失效；5. 核对已处理/未处理、接受/拒绝、任务及审计。
- **预期结果**：合格对象继续，拒绝对象有契约规定的逐项原因，不计安装失败或进入批次；未处理不当作拒绝。准备中断从持久化游标续接，不重复建任务；全部处理完成才编批，全拒绝为 Rejected。准备取消停止后续准入，已建未许可任务受控取消并释放约束，明细保留。
- **证据要求**：EV-HTTP、EV-UI、EV-DB、EV-OPS；固定选择成员、各处理分块及最终数量核对。

### AT-TSK-02｜批次开放、领取与提前下载

- **对应需求**：REQ-CLI-04、REQ-UPD-02、REQ-UPD-03、REQ-UPD-08。依据：详细设计第 6.2～6.4、8.5 节。
- **责任方**：平台验证主责，接入方验证领取及本地保存。
- **前置条件**：多批任务，配置参数已保存；首批含未结束对象、后批尚未开放。
- **操作步骤**：1. 查询和领取首批任务，并在开始时间前下载；2. 并发重复领取并尝试领取未开放批任务；3. 对前批分别留下未终结、需复核失败和超时对象，观察后批；4. 处理前批条件后调度下一批。
- **预期结果**：同一投放最多一个 Open 批次；重复领取返回同一 attemptId。领取/下载不授予安装许可，未开放批不得领取；前批满足未暂缓对象终结及复核条件后才可推进。实例占用在领取前已由准入建立，不因重试领取而增加或消失。
- **证据要求**：EV-HTTP、EV-DB、EV-FILE；批次时序、任务/执行标识、许可记录及下载时间。

### AT-TSK-03｜默认时段、开始许可与错过安排

- **对应需求**：REQ-UPD-03、REQ-UPD-07、REQ-UPD-08。依据：详细设计第 1.2、6.3～6.4、8.4～8.5 节。
- **责任方**：平台验证主责，接入方验证许可保存和本机开始判断。
- **前置条件**：配置默认时段和一次人员覆盖时段；独立任务用于各时间边界；具备受控时钟。
- **操作步骤**：1. 分别省略时段、完整覆盖及只提供半个时段，覆盖厂区跨日默认时段与无效配置；创建后更改服务端配置并对比新旧投放；2. 在允许开始前、恰好开始、最晚开始前、恰好最晚开始和之后请求许可；3. 模拟许可提交后响应丢失，超过截止重取；4. 对错过且未许可对象重新安排；5. 已许可对象跨过时段后提交实际结果，明确未开始的另报 NotStarted；6. 在许可前改变安装版本、数据保护结论或包校验结果。
- **预期结果**：默认与覆盖按设计生效，半个时段拒绝；跨日及厂区时区转换明确，无效必需配置不能用隐含值投放，后续配置不改写旧投放参数快照。仅 `notBefore <= 数据库时间 < latestStart` 且全部条件满足才可获准。旧许可重放不延长 mustBeginBefore，不能用于新的过期安装；未许可错过显示 WindowMissed 等待安排。已许可不被时段结束自动中止，NotStarted 作为未开始取消；开始前条件变化重新核对，拒绝时不提交嵌入的新快照。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；默认配置、保存的时段、服务端边界时间、不可变许可及接入方实际开始记录。

### AT-TSK-04｜明确失败计数、自动暂停和复核继续

- **对应需求**：REQ-UPD-04、REQ-UPD-07、REQ-UPD-08。依据：详细设计第 6.2、6.4、7.1 节。
- **责任方**：平台验证主责。
- **前置条件**：测试参数 B > N，当前批及后续批；含准备阶段失败、安装失败、取消、未知和准入拒绝对象。
- **操作步骤**：1. 逐个提交失败，核对 N−1 和 N 边界；2. 重放失败，穿插拒绝、未知、暂缓、取消和 NotStarted；3. 阈值到达后尝试当前批尚合格任务开始及后批开放；4. 复核指定失败修订后继续；5. 再增加一个未复核失败；6. 对已暂缓的原批对象迟到报告失败。
- **预期结果**：只按明确 Failed 的不同实例计数，下载/校验明确失败包含在内；重复及非失败类别不计数。达到 N 暂停后批，范围为 FutureBatches，当前已开放批仍按时段和其他条件判断。继续不清零历史失败；新未复核失败达到条件再次暂停，迟到失败归原批，可阻止尚未开放后批，不改写其他批统计。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；失败集合、修订号、暂停范围、复核引用及各批统计时间线。

### AT-TSK-05｜等待超时、暂缓与批次归属

- **对应需求**：REQ-UPD-04、REQ-UPD-07、REQ-UPD-08。依据：详细设计第 6.2、6.4、8.4 节。
- **责任方**：平台验证主责，业务验收人核对人工处理提示。
- **前置条件**：分别使 batch.openedAt 早于和晚于 task.notBefore；存在未许可及已许可未回执对象。
- **操作步骤**：1. 核对等待截止 `max(batch.openedAt, task.notBefore) + W`；2. 在截止与严格超过时查询并持续发送进度/重复报告；3. 未处理超时对象时尝试继续，再填写原因并处理或暂缓；4. 原批仍 Open 时恢复暂缓；5. 原批关闭后分别处理未许可和已许可的暂缓对象。
- **预期结果**：超过截止才触发等待超时暂停，进度与重复报告不延长预算；未知不变成成功或失败。未满足处理条件不能继续；暂缓保留占用和原批归属。原批关闭后未许可对象须取消再建重试，已许可对象等待原结果或人工关闭，不能补授新许可；还有暂缓未结束对象时投放不虚报 Completed。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；截止计算输入、暂停原因、暂缓/恢复操作和实例占用前后值。

### AT-TSK-06｜人工暂停、改期、取消与并发开始

- **对应需求**：REQ-AUTH-01、REQ-UPD-03、REQ-UPD-04、REQ-UPD-08。依据：详细设计第 6.2～6.5、7.1、8.4 节。
- **责任方**：平台验证主责，平台研发提供并发与工作中断条件。
- **前置条件**：同一投放包含未许可与已许可对象，多块控制工作；可在关键提交边界安排竞争。
- **操作步骤**：1. 人工暂停与申请开始、任务取消与申请开始分别并发；2. 执行投放改期或取消，工作中尝试新许可、开批和已有许可回执；3. 中断后恢复同一控制工作；4. 查询 Applied/Skipped 明细并尝试另一并行控制；5. 撤销发起主体权限，分别用无权和有权主体尝试接管继续。
- **预期结果**：并发由先提交事实裁决，无检查后绕过；人工暂停阻止未许可开始，不声称停止现场进程。controlPending 时禁止新许可/新开批，已有许可可回执；已许可对象不被改期或强制取消，逐项注明原因。中断保留游标与暂停，工作完成后由人员检查继续；授权失效按设计暂停并记录合法接管，不能借继续扩大权限。
- **证据要求**：EV-HTTP、EV-DB、EV-OPS、EV-UI；事务先后、控制工作/分块/逐项结果、原许可和授权接管审计。

### AT-TSK-07｜受控重试与原任务留存

- **对应需求**：REQ-AUTH-02、REQ-UPD-04、REQ-UPD-08。依据：详细设计第 6.5、8.4 节。
- **责任方**：平台验证主责，接入方验证新旧执行记录区分。
- **前置条件**：已结束失败/取消/人工关闭任务、未结束暂缓任务、已有新占用的实例。
- **操作步骤**：1. 对已结束且仍合格对象建立带原因、时段及重试来源的投放；2. 混入无原任务、原任务未结束和已有其他占用对象；3. 重复提交创建及领取；4. 查询原任务、原回执与新任务。
- **预期结果**：重试生成新的投放、任务及领取后的执行记录，并保存 retryOfTaskId；原任务不重开或覆盖。不合格项逐项拒绝，不计安装失败；重复请求不产生额外新任务或执行记录。接入方按新标识执行，不能拿旧许可替代新许可。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；新旧关联、拒绝原因、时段及审计。

### AT-TSK-08｜重复、乱序、冲突与迟到回执

- **对应需求**：REQ-CLI-01、REQ-CLI-02、REQ-UPD-08。依据：详细设计第 6.6、7.1、8.5 节。
- **责任方**：平台验证主责，接入方配合事件保存和重放。
- **前置条件**：已许可和未许可执行记录；可控制事件顺序、序号及响应丢失。
- **操作步骤**：1. 同 eventId/sequence 同内容重放和异内容重放；2. 先高序号进度，再低序号进度和满足条件的首个终态；3. 终态后提交更高进度及冲突终态；4. 未许可时提交 Installing/Succeeded 及允许的准备失败/NotStarted；5. 与首个终态同时提交新/旧报告快照，核对提交结果；6. 已结束或已取消任务收到附带更新报告序号的迟到回执，再通过独立上报接口提交当前状态。
- **预期结果**：重复仅返回既有结果，不重复计数或释放占用；冲突按 RECEIPT_CONFLICT 等契约语义拒绝。进度不倒退，合法首个终态不会因序号低于进度被丢失，后续进度不能越过终态；许可前不能报告已安装成功。首个有效终态和有效快照按共同事务处理，任务成功本身不推断实际版本或运行状态。已结束/已取消任务的迟到附带快照只留存，不更新现状；实际当前状态须由独立的新有效报告更新。
- **证据要求**：EV-HTTP、EV-DB；原事件摘要、接收顺序、applied、终态、计数及快照前后事实。

### AT-TSK-09｜人工关闭未知及旧回执隔离

- **对应需求**：REQ-AUTH-02、REQ-UPD-04、REQ-UPD-08。依据：详细设计第 6.5～6.6、7.1、8.4、9.2 节。
- **责任方**：平台验证主责验证权限和事务；真实现场核实由接入方与业务验收人负责，见 AT-DATA-03。
- **前置条件**：已许可、超过等待截止仍未知的任务；另备未许可、未超时、无权人员和系统凭据分支。
- **操作步骤**：1. 各不合格分支及缺少原因、现场说明、noActiveInstallationConfirmed 的请求尝试关闭；2. 有权人员按已提供的现场核实材料关闭，注入提交失败后重试；3. 为释放的实例创建新任务；4. 发送旧 attemptId 的进度、成功、失败及旧快照，随后发送独立有效新状态报告。
- **预期结果**：只有符合全部条件的真实人员操作可关闭；ManualClosure、ClosedUnknown、条件释放原占用及审计共同提交，结果仍未知，不计成功或失败。迟到回执归旧任务并标 lateAfterClosure，不能改写关闭结论、推进新任务、释放新任务占用或更新当前快照；新有效报告独立更新实际状态。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；关闭原因、核实说明、人员与时间、事务故障点及新旧任务/占用/快照完整关联。

### AT-TSK-10｜部分回退、兼容声明与开始前复核

- **对应需求**：REQ-UPD-01、REQ-UPD-05、REQ-UPD-06、REQ-UPD-07。依据：详细设计第 5.2、6.1、6.3、8.3～8.5 节。
- **责任方**：平台验证主责校验，接入方提供兼容声明和数据库事实。
- **前置条件**：部分选中实例、未选实例、可用历史正式版；兼容声明及实例上报的组合涵盖有/无数据库、多个数据库、上报未知及模式不兼容；现场材料已提供。
- **操作步骤**：1. 创建选中对象的 Rollback，并混入无声明/未知/不兼容对象；2. 用 Update 指向较低版本，检查绕过尝试；3. 准入后改变数据库 schema 或实际版本，再申请开始；4. 分别提交错误包摘要或数据保护未通过的开始前检查；5. 对兼容对象完成许可和回执，核对声明修订及未选对象。
- **预期结果**：只处理选中且合格实例，拒绝对象有原因；全部数据库须与声明完整匹配，未知不能视为无数据库，版本大小不能推导兼容。低版本不能通过 Update 绕过权限与兼容校验；开始前重新校验且保存依据修订，数据保护未通过不给许可。未选对象无任务变化；现场数据是否完整仍须 AT-DATA-03 证明。
- **证据要求**：EV-HTTP、EV-DB、EV-UI；目标集合、声明与材料修订、准入及开始时数据库状态、拒绝原因和未选对象对照。

## 8. 故障与恢复

### AT-REC-01｜API 与入口节点故障

- **对应需求**：REQ-CLI-04、REQ-UPD-08、REQ-NFR-02。依据：总体架构第 2、7 节，详细设计第 10.1 节。
- **责任方**：厂区运维实施演练，平台验证核对业务与指标。
- **前置条件**：ENV-HA；IN-01、06、09、11 已确认；正常上报、管理请求和下载持续运行。
- **操作步骤**：1. 分别在独立轮次停止一个 API 节点、一个入口节点；2. 在提交前及提交后响应丢失两种时点重放原逻辑请求；3. 检查流量转移、共享会话和权限；4. 恢复节点并核对积压及原连接中断后的重试。
- **预期结果**：健康节点按部署方案继续服务，恢复时间满足预先确认目标；在途连接允许出现有证据的中断并按契约恢复，不声称无缝迁移。写入和许可不因重试重复；未持久化操作不伪报成功，授权与实例事实跨节点一致。
- **证据要求**：EV-HTTP、EV-DB、EV-OPS、EV-METRIC；每轮独立时间线、客户端可观察恢复时点、未明确结果请求的最终核对。

### AT-REC-02｜数据库不可用、切换与旧主隔离

- **对应需求**：REQ-AUTH-02、REQ-UPD-08、REQ-NFR-02。依据：总体架构第 2、7 节，详细设计第 7.1、10.1 节。
- **责任方**：厂区运维主责切换，平台验证与平台研发核对一致性。
- **前置条件**：ENV-HA；数据库复制、切换、旧主隔离方式及 IN-09 已确认；保留已确认与结果不明确请求清单。
- **操作步骤**：1. 数据库不可写时尝试登记、上报、开始许可和审计相关写入；2. 在有并发写入时故障切换，并覆盖网络隔离后旧主恢复；3. 先查询原结果再按原关联重试；4. 比对切换前后许可、任务、占用、审计及客户端可能已执行事实；5. 测量恢复时间和实际恢复点。
- **预期结果**：无法持久化时不以缓存批准新安装或假报审计完成；切换期间保持单写入主节点，旧主不能继续受理业务。结果不明须核对，不重复创建执行许可或误释放实例。任何恢复点差异均可识别并处置；未核清可能已执行的对象前不盲目重新许可。实测恢复点/时间满足预先目标，RPO 目标不能豁免错误任务推进或审计不一致。
- **证据要求**：EV-HTTP、EV-DB、EV-OPS、EV-METRIC；主从角色和复制位置、旧主隔离证据、确认/不明确请求清单及逐项恢复核对。

### AT-REC-03｜多节点调度、租约接管与旧工作者恢复

- **对应需求**：REQ-UPD-02、REQ-UPD-04、REQ-UPD-08、REQ-NFR-02。依据：详细设计第 6、7.1、10.1 节。
- **责任方**：平台验证主责，平台研发与厂区运维提供调度故障条件。
- **前置条件**：多调度工作者；记录租约持有者、代次和截止；至少两个独立投放。
- **操作步骤**：1. 多工作者并发领取准备和开批工作；2. 暂停原工作者至租约到期，新工作者接管后恢复旧工作者；3. 在终态、人工关闭或暂缓提交同时触发批次关闭/下一批开放；4. 注入受控死锁或连接中断，观察同一逻辑操作重试；5. 对比其他独立投放进度。
- **预期结果**：旧代次或到期工作者不能提交推进；同一投放不重复建任务或开批。推进依据已提交终态、失败修订和控制条件，不靠滞后的统计缓存绕过暂停；重试保留操作关联。不同投放不使用一把全厂任务锁，队列领取不会把业务对象悄悄漏判为不存在。
- **证据要求**：EV-DB、EV-OPS、EV-METRIC；租约代次、提交顺序、批次时间线、去重结果与锁等待。

### AT-REC-04｜包副本丢失、损坏和下载续传

- **对应需求**：REQ-REL-08、REQ-CLI-04、REQ-NFR-04。依据：详细设计第 4、7.2、8.6、10.1 节，厂家接入文档第 6.3 节。
- **责任方**：厂区运维实施副本故障，平台验证和接入方核对下载结果。
- **前置条件**：已有核对完成的包及多个副本；IN-02、11 已确认，可受控删除/损坏验收环境副本。
- **操作步骤**：1. 分别移除和修改一个副本，按已配置检测方式触发检查；2. 从其他节点继续下载并修复故障副本；3. 使所有副本不可用，再查询下载与申请开始；4. 断开下载并使用 Range/If-Range 续传，覆盖 206 和切换副本后返回完整 200；5. 接入方对最终文件独立计算摘要。
- **预期结果**：检测后的坏副本停止服务，修复必须核对既定内容，不能替换为其他包。全不可用时拒绝供包和相应开始许可，保留版本历史；任何检测前取得的坏字节也须被接入方摘要核对拒绝。206 按有效范围续写，完整 200 重新写文件；ETag 不当作 SHA-256，丢包或下载中断不生成安装成功。
- **证据要求**：EV-HTTP、EV-FILE、EV-OPS、EV-METRIC；故障检测时点、各副本摘要、Range 响应、客户端最终校验及许可拒绝证据。

### AT-REC-05｜上传、复制、清理中断及下载记录恢复

- **对应需求**：REQ-AUTH-02、REQ-REL-08、REQ-REL-09、REQ-UPD-08。依据：详细设计第 7.2～7.3、10.1 节。
- **责任方**：平台验证与厂区运维主责，平台研发提供文件工作观测点。
- **前置条件**：独立文件工作、至少两副本；可控制字节落盘、最终路径切换、数据库结果提交和下载日志交付。
- **操作步骤**：1. 分别在上传、复制及删除的字节操作前后和数据库提交前后中断；2. 重启并按同一工作标识核对/续接；3. 将复制或修复工作者暂停后推进清理，再恢复旧工作者；4. 丢失传输结束记录或使下载节点失联，尝试清理；5. 补交可信结束记录或带节点代次的进程终止证据，再重复交付日志并清理。
- **预期结果**：先有持久化工作再操作文件，暂存不直接可下载；部分删除按实际文件续接，全部核实后才登记完成。包级文件互斥与阶段/代次复核阻止旧工作者复活已清理包，单凭数据库租约过期不能证明文件操作结束。下载记录缺失不能按超时放行清理；日志重放去重，业务历史与下载审计不丢失。
- **证据要求**：EV-DB、EV-FILE、EV-OPS；每个中断点实际文件清单、工作游标、文件互斥/代次检查、清理等待原因及可信结束证据。

### AT-REC-06｜客户端断线、重启和恢复上报

- **对应需求**：REQ-CLI-07、REQ-UPD-03、REQ-UPD-04、REQ-UPD-08。依据：详细设计第 5～6、10.1 节，厂家接入文档第 6 节。
- **责任方**：接入方与平台验证主责。
- **前置条件**：保存稳定身份、任务、执行及事件标识的客户端；分别在领取前、下载中、许可响应丢失、执行中和回执响应丢失处断线。
- **操作步骤**：1. 按各故障点切断 API 访问或重启客户端；2. 观察五分钟状态与任务等待超时；3. 恢复连接后建立适当报告流、查询原任务并按原关联重试；4. 覆盖未许可错过时段、已许可已开始及已许可确认未开始；5. 检查本机重复执行保护和新报告事实。
- **预期结果**：断线只导致按规则显示未知/等待，不能自动成功、失败或释放未知执行。有效任务可继续查询领取；已存在执行不重复建立，过期许可不能用于新安装。接入方区分已经执行、未开始和仍未知，按契约上报并避免本机重复安装；平台结果与新状态报告分别处理。
- **证据要求**：EV-HTTP、EV-DB、EV-UI、EV-OPS；接入方本地标识、实际执行次数和恢复决策。涉及本机数据完整性的证据另由 AT-DATA-02 提供。

### AT-REC-07｜备份恢复与重新开放业务前核对

- **对应需求**：REQ-AUTH-02、REQ-REL-06、REQ-REL-09、REQ-UPD-08、REQ-NFR-02。依据：总体架构第 6～7 节，详细设计第 10.1 节。
- **责任方**：厂区运维主责恢复，平台验证核对平台事实，接入方配合现场现状核实。
- **前置条件**：已确认 IN-01、02、09；独立恢复环境及数据库、不可变包清单、身份恢复材料和审计引用的备份；准备恢复点后可能已获准/已执行的任务。
- **操作步骤**：1. 从备份恢复到隔离环境并保持新安装许可关闭；2. 核对版本、包清单、实际副本、身份、历史、未结束任务和占用；3. 引入缺包、坏包及备份后已执行但恢复库未体现的分支；4. 依据客户端和操作证据核实恢复点差异并修复/隔离对象；5. 在条件满足后受控开放，测量从恢复启动到业务可验证恢复的时间。
- **预期结果**：在线冗余副本不代替备份；缺失/损坏包不被标为可用。恢复点后可能执行的对象未核实前不盲目重发许可，身份与历史可追溯且无错误新任务推进。恢复点、恢复时间满足事先目标；差异、无法恢复部分及处置均明确记录，不能隐瞒后称通过。
- **证据要求**：EV-DB、EV-FILE、EV-OPS、EV-METRIC，必要的 EV-SITE；备份来源/时点/摘要、逐项核对清单、差异处理和重新开放依据。

## 9. 厂家现场数据保护

三项现场用例由接入方执行本机操作并承担数据保护责任，平台保存任务、报告、声明和材料引用。平台验证人员只凭服务端记录不能确认现场通过。支持矩阵中每一类存在不同安装、数据库迁移或回退行为的组合，均须有对应执行证据；相同行为的代表性选择须在 IN-10 中说明依据。

### AT-DATA-01｜正常更新后的数据完整性与业务可用性

- **对应需求**：REQ-CLI-01、REQ-UPD-06、REQ-NFR-04。依据：需求规格 REQ-UPD-06，详细设计第 5.2、8.3、8.5 节，厂家接入文档第 7 节。
- **责任方**：接入方主责，业务验收人确认现场结果，平台验证核对平台证据关联。
- **前置条件**：ENV-SITE，IN-10 已确认；真实旧版、待更新包及代表性数据库/日志/其他保留数据；记录数据位置和预期迁移行为。
- **操作步骤**：1. 固定基准记录和业务校验点，保存可恢复副本及日志截止位置；2. 按完整平台流程校验包、申请开始并执行更新；3. 核对基准关键记录、关系、内容和迁移预期，执行代表业务读写；4. 核对原日志保留和新日志衔接，确认数据位置未被安装内容覆盖；5. 上报实际版本和结果，并关联现场材料。
- **预期结果**：关键历史数据完整可读，正常业务可用；合法新增/迁移与预期相符，数据库、日志和其他保留数据没有被重置或丢失。客户端独立校验包，不以 API 目标版本代替实际版本上报；平台成功回执和现场验收结论分别有证据。
- **证据要求**：EV-SITE、EV-HTTP、EV-DB、EV-FILE；关键数据前后核对、业务操作、日志连续性和接入材料修订引用，含实际执行人与验收人。

### AT-DATA-02｜更新失败、恢复及避免重复本机执行

- **对应需求**：REQ-UPD-06、REQ-UPD-07、REQ-UPD-08。依据：详细设计第 5.2、6、8.3 节，厂家接入文档第 6～7 节。
- **责任方**：接入方主责恢复，业务验收人确认业务及数据，平台验证核对任务事实。
- **前置条件**：ENV-SITE，已确认厂家恢复方案和安全可重复的故障点；有可恢复数据副本，不将方案文本当作恢复已验证。
- **操作步骤**：1. 分别在下载校验、本机文件替换、适用的数据库迁移及回执响应阶段制造代表性失败/中断；2. 按厂家方案恢复，保留本机执行记录；3. 重启及重放原任务消息，确认是否曾取得许可和实际执行状态；4. 核对关键数据、日志和业务，报告失败、未开始或实际结果；5. 如需新任务，按受控重试流程执行。
- **预期结果**：失败不能覆盖、重置或丢失必须保留的数据库、日志及其他现场数据；恢复后业务、数据和日志连续性达到 IN-10 的已确认标准。不能直接回退的数据库变更有可验证恢复路径；同一执行记录不因响应丢失或重启重复安装。平台保留原失败/未知事实与新任务关联，不用“恢复完成”掩盖原结果。
- **证据要求**：EV-SITE、EV-HTTP、EV-OPS；每一故障点的执行/恢复时间线、数据核对、恢复材料修订、本机执行次数及平台关联。

### AT-DATA-03｜实际部分回退和人工关闭前的现场核实

- **对应需求**：REQ-UPD-04、REQ-UPD-05、REQ-UPD-06、REQ-UPD-07、REQ-UPD-08。依据：详细设计第 5.2、6.5、9.2 节，厂家接入文档第 6.5、7 节。
- **责任方**：接入方执行回退并核实现场，业务验收人确认，获授权管理员执行平台关闭，平台验证核对关联。
- **前置条件**：ENV-SITE，兼容及不兼容历史目标、选中与未选实例；另备已获准但长期无回执对象和可靠现场核实办法，IN-10 已确认。
- **操作步骤**：1. 在选中兼容实例执行完整回退，核对现场数据库、日志、业务和未选实例；2. 验证不兼容/未知目标的拒绝及替代恢复方案；3. 对未知任务现场核实实际安装活动已停止，形成说明与证据后由管理员关闭；4. 重新安排该实例，再投递原执行的迟到回执并上报真实当前版本。
- **预期结果**：只回退选中且兼容对象，未选实例不被平台或接入方连带修改；回退后的关键数据、业务和日志满足标准。人工关闭之前确实无安装在执行，关闭仍保持结果未知，不能把现场“已无进程”当作此前安装成功。新旧任务隔离，实际当前状态由新上报确认；恢复方案有现场核对支持。
- **证据要求**：EV-SITE、EV-HTTP、EV-DB、EV-UI；兼容声明、回退前后数据和业务结果、未选对象对照、无活动安装核实材料、关闭人员和新旧回执关联。

## 10. 容量与持续运行

以下五项必须在 ENV-CAP 的单厂基准上验证。每个实例使用独立身份，报告至少每分钟一次；版本、任务和回执的协议模拟结果须明确标为模拟，不代替第 9 节真实现场验收。IN-01～09、11 未确认前，涉及定量通过条件的项目保持待条件确认。

### AT-CAP-01｜十万实例持续报告与集中上报

- **对应需求**：REQ-CLI-01、REQ-CLI-07、REQ-NFR-02。依据：总体架构第 6 节，详细设计第 5.1、10.1 节。
- **责任方**：平台验证主责，厂区运维确认环境和指标。
- **前置条件**：5 万设备标识、10 万实例与独立凭据/报告流已核对；IN-01、05～07、11 已确认；发生器有独立资源监控。
- **操作步骤**：1. 在约定预热后持续发送每实例至少每分钟一次的新报告，分别执行错峰和集中报告模式；2. 按计划到达时间发压，不因响应变慢而悄悄减少计划量；3. 同时记录计划、发出、接收、接受和超时请求及序号；4. 采集数据库、连接池、CPU/内存、锁等待与积压；5. 核对当前快照、版本证据和新鲜度。
- **预期结果**：在确认的报告规模和时长下满足延迟、错误率、积压及消退目标；每个实例有可核对的接收记录，不只用总 RPS 代替实例覆盖。发生器排队与服务端延迟分别计量，重试不能凑成新的有效报告。快照量与保留策略相符，不将约 1.44 亿次/日调用预算等同于必须保存的历史行数。
- **证据要求**：EV-METRIC、EV-DB、EV-OPS，抽样 EV-HTTP；实例覆盖清单、完整负载计划、集中/错峰两组曲线和发生器资源证据。

### AT-CAP-02｜报告与查询、网页、目标筛选混合负载

- **对应需求**：REQ-CLI-03、REQ-CLI-04、REQ-UPD-02、REQ-NFR-02、REQ-ASSET-04。依据：详细设计第 6.1、8、10.1 节。
- **责任方**：平台验证主责，业务验收人与厂区运维确认负载构成。
- **前置条件**：持续报告基准；IN-01、04～07、11 已确认，包含实际软件分布及大软件集中规模。
- **操作步骤**：1. 叠加约定比例的版本查询、任务查询、管理分页和人员网页操作；2. 执行按工序/设备编号/软件/IP/状态的组合筛选及设备多软件权限过滤及大量成员封存；3. 观察大软件与其他软件并行访问；4. 核对列表查询数量、执行计划、连接和锁等待；5. 对各主体抽样核对返回内容与权限。
- **预期结果**：各类请求分别达到目标，混合负载不使报告或其他软件长时间失去服务；容量不能靠遗漏权限检查或字段实现。组合查询按页批量取关联，不产生逐行数据库查询；筛选快照、并发列表与封存成员语义保持正确，队列和连接受配置约束。
- **证据要求**：EV-METRIC、EV-DB、EV-UI、EV-OPS；业务比例、软件分布、查询计划/数量与分类延迟，说明真实浏览器与协议流量各占比。

### AT-CAP-03｜大批量准入、逐台进度和分批投放

- **对应需求**：REQ-UPD-01、REQ-UPD-02、REQ-UPD-04、REQ-UPD-07、REQ-NFR-02。依据：详细设计第 6、8.4、10.1 节。
- **责任方**：平台验证主责，厂区运维采集资源，业务验收人核对进度可读性。
- **前置条件**：10 万实例按已确认软件分布准备目标集合，并包含约定的单软件最大投放；IN-01、04～08、11 已确认；模拟器会领取及返回不同结果。
- **操作步骤**：1. 分块封存大集合并创建投放，持续查询逐项准入和逐台进度；2. 按配置分批领取、申请开始并报告模拟结果；3. 混入不合格对象、重复调用、明确失败、超时、暂停及继续；4. 在准备/控制期间中断工作者并恢复；5. 核对目标、任务、批次、实例占用及最终统计。
- **预期结果**：异步受理、准备完成和后续执行时间分别满足约定目标；单次请求和事务不因目标数无界增长。已处理=接受+拒绝，所选=已处理+未处理；接受任务的成功/失败/取消/人工关闭未知/未结束数量可逐台对账。配置的开放和暂停规则保持有效；Completed 仅表示跟踪结束，模拟成功不能证明现场安装。
- **证据要求**：EV-HTTP、EV-DB、EV-UI、EV-METRIC、EV-OPS；封存集合摘要、逐项结果、任务/批次统计、工作恢复游标和模拟器结果标识。

### AT-CAP-04｜并发下载、续传与 API 负载隔离

- **对应需求**：REQ-REL-08、REQ-NFR-02、REQ-NFR-04、REQ-NFR-05。依据：总体架构第 2、6 节，详细设计第 7.2、8.6、10.1 节。
- **责任方**：厂区运维测量网络和节点，平台验证主责负载与判定，接入方提供代表包。
- **前置条件**：IN-01～08、11 已确认；真实代表包及 SHA-256、可用带宽测量；持续报告和约定查询同时运行。
- **操作步骤**：1. 按约定批次和并发请求包，逐个计算最终摘要；2. 引入断流、Range 续传和整包重取，记录实际链路流量；3. 分别测量一个包节点退出及恢复后的下载；4. 核对下载鉴权、API 响应、数据库负载和完整下载完成时间。
- **预期结果**：下载和恢复完成时间、吞吐及同时运行的 API 指标达到约定目标；API 不转发包字节。仅校验完整的文件计作完成，重传字节不增加独立完成数量；断流与摘要失败不产生安装成功。结果明确绑定包组合、带宽、拓扑、并发及重试策略，不能外推为所有厂区固定完成时间。
- **证据要求**：EV-METRIC、EV-FILE、EV-HTTP、EV-OPS；独立完整文件数、有效字节、链路总字节及重传量、各网段/节点吞吐和 API 对照曲线。

### AT-CAP-05｜持续混合运行、断线恢复突发与积压消退

- **对应需求**：REQ-CLI-07、REQ-UPD-08、REQ-NFR-02、REQ-NFR-05。依据：总体架构第 6～7 节，详细设计第 10.1 节。
- **责任方**：平台验证与厂区运维主责，接入方确认重连节奏可实现。
- **前置条件**：IN-01～09、11 已确认；十万实例的报告、查询、任务和下载混合模型；明确断线比例、持续时间及重连分布。
- **操作步骤**：1. 按确认时长持续运行并观察资源趋势；2. 使约定规模实例同时或分组断线，随后按已确认节奏恢复；3. 单独轮次叠加一个 API 节点或一个下载节点故障；4. 从故障发生持续采集到恢复后稳定观察阶段；5. 对账报告、任务、下载、重试与未明确结果。

- **证据要求**：EV-METRIC、EV-OPS、EV-DB；全时段原始数据、断线/重连计划与实际曲线、资源增长趋势、积压消退和结果核对清单。

## 11. 测量口径与执行顺序

### 11.1 指标及计算方法

下表定义验收测量口径，不为产品新增 API 字段。所有计算均保留原始样本、时间范围、过滤规则和分母，正常期、故障期和恢复期分别呈现。

| 指标 | 记录与计算要求 |
|---|---|
| 请求量和覆盖 | 分接口记录计划、实际发出、到达/接受、完成、超时和重试次数；逻辑业务操作与 HTTP 尝试次数分开。上报另记录活跃实例数及每实例最新有效序号/间隔 |
| 请求延迟 | 按接口记录 p50/p95/p99 及最大值；发生器排队、网络往返和可观测服务端处理时间分开。超时单列，不能删掉慢请求后计算“全部延迟” |
| 错误率与限流 | 传输失败、5xx、429、非预期 4xx 分别计数并给出尝试次数分母；脚本刻意触发且符合契约的拒绝单列，不能把生产负载下的限流全部排除以获得通过结论 |
| 积压与任务完成 | 持久工作待处理项、最老等待年龄、准备/控制游标、未完成及未知任务数；记录故障后停止增长和恢复至目标范围的时点，不能只看已处理百分比 |
| 数据库与节点负载 | CPU、内存及增长、磁盘/网络吞吐与延迟、连接占用、事务时长、锁等待/死锁、复制延迟；说明采样间隔，保留峰值而非仅平均值 |
| 下载 | 有效吞吐=校验完整且去重的下载字节数/观测时间；链路总字节与重传开销另列。记录每包与整批完成分布，下载完成不等于安装完成 |
| 恢复时间 | 明确故障发生、发现、切换/修复完成、客户端可成功访问、积压消退五类时点；用 IN-09 约定的起止点判定，不把进程启动当作业务已恢复 |
| 恢复点 | 比对已确认提交、结果不明确、恢复后存在三类事实及其时间/序列，计算恢复点差异；数据库、包清单和身份材料分别核对，不能只检查数据库能启动 |

包下载时间的预估使用实测包总量、有效带宽及并发/重传开销，作为 IN-08 的确认依据。测试结果须同时报告实际完成条件，不以理论带宽直接宣称通过。
